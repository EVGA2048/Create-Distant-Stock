# 离线节点不再阻塞在线节点：0.3.60 / Transerver 0.1.1

## 根因与修复

旧实现一直读取按文件名排序的前 128 条消息，而消息要等最终回执才删除。离线节点的消息可以永久占住整个批次。Router 接收队列也有相同问题；Transport OK 不能证明业务消息已送达。

- 发送队列、接收队列、Router 队列与回执队列使用轮转游标。新消息有有限优先额度，历史消息仍有处理额度；重启后从持久化队列恢复。
- 每轮最多转发 16 条，Router 每次最多返回 32 条消息，消息批次总量最多 4 MiB（另有少量编码头）。单消息载荷仍限制 2 MiB；HTTP 客户端在读取过程中拒绝过大响应。
- 主线程不再同步调用 Transerver.send 的磁盘持久化；由一个后台发送线程处理，等待队列最多 128 项、排队数据最多 8 MiB。包裹仅在持久化成功后标记 SUBMITTED；等待提交时不超时退件，也不提前消费其回执。
- 新发送的未完成消息按目标节点限制：普通消息最多 64 条、8 MiB；全局最多 512 条、32 MiB。握手和网络公告按目标与频道合并，保留控制消息额度。额度随最终回执释放；这些限制不会删除已有积压或包裹。
- 启动时的旧格式公告与握手后的目录公告使用不同的合并代次。旧格式消息仍在等待回执时，包含远仓网络目录的新公告也会立即入队，避免协议已 compatible、网络列表却为空。
- 库存查询、接收端探测及周期公告有效期为 120 秒，避免目的地恢复后执行过时查询。过期判定仍由接收端完成，发送端不会擅自把已投递包裹判为失败。
- 处理器完成回调只入队，回执落盘由 Transerver pump 执行。每频道最多 32 个异步处理中消息、全局最多 128 个，避免一个卡住的业务频道占满所有处理额度。
- 队列计数缓存文件名，不再为状态展示读取所有载荷；Router 工作线程与工作队列有界，wake 请求合并；并发发送在落盘前登记回执等待者，避免快速回执丢失。

这里移走的是传输发送/回执磁盘操作。Minecraft 世界对象、物品编解码和 SavedData 的既有一致性操作仍由服务器线程负责；没有宣称所有游戏逻辑都异步化。

1. 安排维护窗口，正常停止 ES2、VL4 游戏服和 VL4 上的独立 Router，备份世界、配置和 Transerver 数据目录。

4. 先启动 Router，再启动两服。保留 node-identity、密钥和全部队列；不需要删除 ad5b4a08 测试节点来绕过此问题。队列文件现在有进程内索引，不要在服务运行中手动修改队列目录。

## 现场验收

- 两服 `/transerver status` 正常；约 1–2 分钟内 `/distantstock doctor` 应识别另一在线节点为 compatible。已下线测试节点仍可显示 unknown，这是预期；旧 dead 记录不会自动清除。
- ES2 `/distantstock network` 应看到 VL4 网络；用邀请码加入，验证终端绑定。历史 outbox 不必清零才可看到新公告。
- 双向各测试一笔小额取货、库存查询和包裹到达，核对物品数量与退件行为。
- 保持测试节点离线，重复跨服发现/加入/传输；停一台游戏服再启动，检查另一服本地功能正常，恢复后消息继续推进且没有重复入库。
- 观察主线程耗时、堆内存、队列增长和错误日志；本地并发回归不能代替生产整合包与实际在线人数下的负载验证。

## 持久化边界

Transerver 保持至少一次投递语义，应用处理器必须保留原来的幂等账本。处理器 future 完成到下一次 pump 落盘之间发生崩溃，消息可能重新投递；不能把 Java future 完成理解成已经完成最终回执持久化。新游标和优先提示不承担消息所有权，丢失它们不会删除持久化队列。
