## 1. 配对码（跨服唯一可行的寻址与授权）

### 为什么非要它

港组是**每台服务器自己的**（存在那台服务器的存档里）。名字在两边各算各的 ——
A 服的「仓库」和 B 服的「仓库」是**两个不同的组**。
你在 A 服能选的目标组只有 A 服本地的，**对面 B 服的组你这边没有任何途径指过去**。
而你又不可能走到 B 服去右键那台港。所以跨服缺的不是界面，是
**「两边的组怎么互相认识」这件事本身**。

### 规格

```java
public record PairingCode(String code, UUID group, UUID issuer,
                          long expiresAt, int usesLeft, boolean crossServer) { }
```

| 规则 | 值 / 说明 |
|---|---|
| 长度与字符集 | **6 位**，去掉 `0/O/1/I`（手抄 + 聊天框里打字） |
| 有效期 | 默认 **10 分钟**，上限 1 小时 |
| 次数 | **一次性**：兑换成功 `usesLeft--`，到 0 删除 |
| 谁能生成 | **组主**（`DockGroup.ownedBy`）。授的是使用权，不是所有权 |
| 兑换后发生什么 | **双向**：兑换者的组/网络出现在对方成员表里，对方也出现在兑换者的表里 |
| 是否落存档 | **落**（`PairingCodes extends SavedData`，照 `DockGroupDirectory` 的形状写），靠过期兜底 |
| 撤销 | 组主从成员表删人；**已在途的包裹照落**（承诺已做出，跨服撤不回），新订单一律拒 |

### 实现落点

- `routing/PairingCodes`（`SavedData`）：键是码，值上面那个 record。
- `routing/PairingCode`：生成时用 `SecureRandom`，校验时大小写不敏感、忽略空格与连字符。
- 网络：`PairCodeC2S`（生成 / 兑换两个动作）、回包复用 `DockGroupsS2C` 刷新列表。
- 跨服：码要带**网络指纹**（`RemoteNetworkId.shortLabel()`），兑换时对不上直接拒——
  防止码被贴到公开频道后被不相关的人兑走（这不是安全边界，是防手滑）。
- 权限：把 `DockGroup.admits` 拆成 `canSend` / `canBuild` 两个问句
  （见 `PERMISSIONS-PROPOSAL.zh-CN.md`，判定位全仓只有四处调用，改动面可控）。

### 验收

- gametest：兑换一次后码消失；过期码拒；用尽码拒；错指纹拒；
  **撤销后新订单被拒、在途包裹仍落地**。

### 2026-09-16 实施记录（与草稿的差异都在这里）

**1. 码不带网络指纹，改成「群发问一遍」。** 6 位码装不下节点 id，而兑换方本来就只认识
`TranserverBridge.knownNodes()` 里的那几个节点：于是兑换时向**每个已知节点**发一条
`pair.claim`，持有这个码的那台回 `pair.grant`（带 groupId + 组名 + 它的节点 id），其余静默。
一条小消息 × 节点数，换掉指纹解析和「码里塞 id」的整条路。10 秒没人应答就是
「没有服务器认领」——和「对面明确拒绝」是两句不同的话，两种都说了。

**2. 本服的码在本服兑换会被拒**，并且告诉玩家「直接选『组名』就行」。因为本服组在下单时
要过 `DockGroup.admits`，把本服码变成远端目的地会得到一个「能选、下单时才被拒」的目的地。

**3. 「远端组」到底指哪一边 —— 这条推翻了草稿的一半假设。**
`TranserverOrderService` 接单时建的路由是 `(record.sourceNodeId(), receivingDockGroupId)`：
**下单方**才是收货节点。所以：
- 目的地是**本服**的组（默认形态）→ 货从对面仓库出来、**寄回下单方**，落在下单方选的那个组；
- 目的地是**对面**的组（只有配对码能指过去）→ 货留在对面，落在对面那个组（新加的分支，
  `destinationNode()`：组在本服目录里且不是默认组 → 目的地就是本机）。

于是配对码的用途精确地是后者：**向乙服的仓库下单，货交给乙服那边的港**；以及
`/distantstock dock send-to <远端组名>` 把港指过去直接发货。

**4. 界面入口不是新按钮，是目的地下拉框的最后一行**：那一行写「＋ 生成配对码：<当前组名>」，
点它就给组主自己生成（服务端校验所有权）。**兑换**则是在同一个目的地输入框里**输入 6 位码回车**
—— 码和名字是同一件事（「一个还不在这里的目的地」），按形状区分即可，也就省掉了一个框、
一个按钮和它们要占的版面。下拉框里远端组画成 `标签·组名`（标签是节点 id 前 8 位；Transerver
不给节点显示名），紫色以示区别。

**5. 落点**：`routing/PairingCodes`、`routing/RemoteGroups`、`link/PairingWireCodec`、
`link/PairingService`、`net/PairCodeC2S`、`net/RemoteGroupsS2C`；
目的地的两处解析（`RequesterMenu` 的按名解析、`BindGaugePanelC2S` 的面板目的地）都加了
「本地优先、其次远端」的兜底；`PlaceOrderC2S.resolveGroup` 放行远端组 id。

**6. 没做的**：一次性/过期是**发码方**的属性，兑换后 A 那边存的只是一行记忆 ——
所以**撤销**只能是「忘掉自己这边的目的地」，不能让对面收回。真正的收回要在**包裹投递时**
校验来源玩家，而订单线上现在只带得动一个组 id、带不动「谁下的单」（`LinkQueues.Order.from`
是字符串名）。那是下一版的事，记在 `PERMISSIONS-PROPOSAL` 里。

### 断开（用户 2026-09-16 问「以后想拆掉和断开行不行」）

| 想要 | 现状 |
|---|---|
| B 删掉那个组 | ✅ 界面里组主那行按「×」两次；组里港退回默认组，不拆港不丢包裹 |
| B 拆掉接收港 | ✅ 再发来的包裹在 B 落地时找不到港 → 回退面 / 退件箱，包裹会回到 A 的发送港 |
| B 撤回**没被兑换**的码 | ✅ `/distantstock pair revoke <码>` |
| B 关组（○/●）断掉跨服 | ❌ **没用**：`admits` 的四处调用全在这台服务器内部，跨服投递不做来源校验 |
| A 忘掉远端目的地 | ✅ 远端那行按「×」两次 / `/distantstock pair forget <远端组>`（2026-09-16 补） |
| B 彻底拉黑 A | ❌ 没有；同上，需要投递时校验来源 |

结论：**断在物流层面是成立的**（对面删组/拆港，包裹会被退回来），但**没有拒绝机制** ——
对面删了组，A 还是会发货，只是货会原路退回。要真正「拒之门外」得等权限那一版。

## 5. `DockItem` 那一刀

- `DockItem extends BlockItem` → **`extends LogisticallyLinkedBlockItem`**，
  白拿两件事：**已调谐时的附魔光效**、**右键已联网方块抓取那个网络的频率**。
- **覆写 `place()` 允许未调谐放置** —— Create 那个基类默认「未调谐拒绝放置」，
  但**接收端的港根本不需要频率**，强制的话等于逼对面玩家去绑一张他可能没有的网络。
  用户明确要求：对端的港不能「先绑定后放置」。
- 分辨率问题：**频率**走「先绑定后放置」（本地物理操作），
  **组/地址**走「放下之后设」（必须能远程传达，这正是配对码的用途）。

## 6. bug：监视器的「开关自锁」（用户 2026-09-16 报）

> 「在监视器里面关掉开关以后监视器就显示『未接入塔』了 —— 相当于我在吊扇上面装了一个开关，
> 转起来了我就碰不到他了。」

**根因**：监视器的塔页要求它**正在被带载**才画得出来。

- `TowerReadout.describe(carrier, facts, usage, side)`：`facts` 为空就 `return NONE`（＝未接入塔）；
- `carrier` 来自激活快照里「谁在带载这个位置」，也就是**被带载集合**；
- 于是：关掉监视器自己的开关（带载/区块开关）→ 它不再被带载 → 没有 carrier → 塔页整个不画 →
  **那个能把它打开的开关也就没地方可按了**。自锁。

**修法**：监视器「我在哪座塔下」必须**按几何算**，与是否被带载无关。

1. 加 `TowerActivation.towerAt(level, pos)`：返回激活半径**包含**这个位置的塔（多座取最近），
   完全不看带载集合；
2. `TowerReadout.survey` 里：`carrier(pos)` 有就用它，没有就退到 `towerAt(pos)`；
3. `attached = false` 只在**真的没有任何塔的半径覆盖我**时出现 —— 那才是「未接入塔」的本意。

被带载数、预算、上限这些**照旧**（它们本来就该反映真实带载），只是「页面能不能画出来」
不再依赖它。

**2026-09-16 实施（与上面的草稿有一处改动）**：`towerAt` 不读激活快照，**直接读已加载的塔方块**
（`LoadedTowers` + `tier().radius()`）。快照里的系统只由**正在转动**的塔构成 —— 从快照取
「我头上是哪座塔」，会让暂停的塔也把页面收走，而「转速不足」恰恰是那一页要显示的东西。
按方块读还额外解决一件事：`survey` 里本来就有「被带载但不在任何系统里」（`members.isEmpty()`）
那条分支，塔停转时正好落进去，页面照画、读数显示 `stopped` + 转速 0。

**为什么不用「真转起来的塔」写端到端测试**：`TowerActivationGameTests` 的类注释写着 ——
gamethub 的竞技场只隔 13 格，而塔的半径是 32，一座真转的塔会把同批次所有别的用例的设备关掉。
所以该用例用 `pinDevice(..., active=false, carrier=null)` 把「被关掉且没被带载」这个**状态**钉住，
塔本身是真的（只是没通轴），几何查找故意**不过** pin 层。两条用例在 `TowerGameTests`：
`aMonitorBesideATowerAttachesToIt`（不再需要 pin）与 `aMonitorNotCarriedStillGetsItsTowersPage`。
