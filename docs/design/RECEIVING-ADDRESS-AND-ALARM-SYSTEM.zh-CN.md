## 1. 玩家概念：从“接收港组”改为“接收港地址”

“港组”继续可以作为代码内部概念（`DockGroup`），但不再作为主要玩家术语。
玩家面对的是：

**接收港地址（Receiving Dock Address）**

它表示“一批远仓港共同接受的逻辑目的地”。例如：

- `中央仓库`
- `工业区`
- `峡浪洲`
- `RMA-04`

这样做有两个原因：

1. Create 本身已经使用“地址”表达包裹应去哪里，远仓沿用同一种物流语言；
2. 玩家真正关心的是“这件货寄到哪里”，而不是内部有多少个港组成一组。

### 1.1 与 Create 包裹地址的区别

两种地址不能混为同一字段：

- **接收港地址**：决定远仓包裹最终落到哪一组远仓港，可能跨服务器；
- **包裹地址**：Create 原生地址，决定包裹落地后在该服务器本地物流中如何继续分拣。

推荐玩家界面固定使用这两个完整称呼，避免只写一个模糊的“地址”。

典型流程：

```text
远程仓库
  ↓ 按“远端包裹地址”打包
远仓港
  ↓ 按“接收港地址”跨服寻址
目标服务器的远仓港
  ↓ 切换为“本地包裹地址”（若配置）
Create 本地物流
```

## 2. 接收港地址必须在远仓网络内唯一

同一个 **远仓网络（Distant Stock Network）** 中，**不允许存在两个同名接收港地址**。

Transerver 只是节点间传输基础设施，不再等于一个巨大的玩家物流域。不同远仓网络之间可以合法重名：

```text
Nexus / 工业区 -> UUID-A
SNC   / 工业区 -> UUID-B
```

两个地址处于不同远仓网络，彼此不可见，也不会互相参与解析。

同一个远仓网络里则仍然禁止重名：

```text
Nexus
├─ A 服：工业区 -> UUID-A
└─ B 服：工业区 -> UUID-B   ← 冲突
```

所以真正的逻辑键是：

```text
(DistantNetwork UUID, ReceivingAddress Name)
```

而不是：

```text
(Transerver 全域, Name)
```

### 2.1 身份与名称

- `DockGroup.id` / UUID：稳定身份；
- `DockGroup.name`：玩家使用的逻辑地址名，在所属远仓网络内唯一；
- `DockGroup.distantNetworkId`：地址所属的远仓网络；
- `node`：这个地址当前属于哪个服务器节点；
- `docks`：当前使用这个地址的接收港。

UUID 仍是协议和存档中的真正身份。玩家输入名称时，解析器必须先确定当前远仓网络，再在该作用域内解析地址。

### 2.2 名称比较规则

首版建议：

- 去除首尾空格；
- 大小写不敏感；
- 不自动改名；
- 不允许同一远仓网络内同名创建；
- 不允许重命名成同一远仓网络内已存在的本地或远端地址。

### 2.3 网络分区造成的冲突

同一远仓网络的节点断开时，A、B 两边可能同时创建同名地址。恢复连接后不能猜谁赢。

检测到：

```text
Nexus / A: 工业区 -> UUID-A
Nexus / B: 工业区 -> UUID-B
```

应进入 **ADDRESS CONFLICT**：

- 两个对象都保留，不自动删；
- 该名称不能继续用于新订单或新路由；
- 终端、日志台和护目镜明确报警；
- 由其中一方重命名后解除冲突。

禁止：

- UUID 小的自动获胜；
- 后出现的自动加 `_2`；
- 本地地址静默覆盖远端地址；
- `findByName()` 随便返回其中一个。

远仓的原则仍然是：**不知道该把货送到哪里，就不发送。**

### 2.4 当前代码

当前实现已经按 `distantNetworkId + name` 做地址作用域，并由 `ReceivingAddressResolver` 统一解析本地与远端地址。

旧存档没有 `distantNetworkId` 的地址进入隐藏的 `Legacy` 作用域；仓储网络迁入正式远仓网络后，Legacy 地址仅作为兼容回退，不会覆盖正式作用域内的同名地址。

### 2.5 远仓网络不是 Transerver 节点列表

远仓网络是 Distant Stock 自己的玩家物流域，位于 Create 仓储网络之上：

```text
Transerver
├─ ES2 节点
│  └─ Create 仓储网络 A
├─ Parallel 节点
│  └─ Create 仓储网络 B
└─ SNC 节点
   └─ Create 仓储网络 C

远仓网络 Nexus
├─ Create 仓储网络 A
└─ Create 仓储网络 B

远仓网络 SNC
└─ Create 仓储网络 C
```

每张 Create 仓储网络最多加入一个远仓网络。远仓网络拥有稳定 UUID，并可由创建者生成一个长期加入码，例如：

```text
1F2A-5B7G
```

加入码只用于“把本地 Create 仓储网络加入远仓网络”的握手。加入成功后各节点保存远仓网络 UUID；后续路由、公告和地址解析都依赖 UUID，不依赖加入码。

加入码可以重置；重置只影响未来加入，不会让已经加入的仓储成员掉线。

## 3. 公开地址与私密地址：保护“发现”，不是保护“投递”

公开 / 私密首先是**信息可发现性**，不是运输权限墙。

| 行为 | 公开地址 | 私密地址 |
|---|---|---|
| 终端自动补全 | 显示 | 不显示 |
| 地址浏览列表 | 显示 | 不显示 |
| 港口/护目镜公开显示地址名 | 显示 | 隐藏或显示“私密地址” |
| 已知准确地址名后手动输入 | 可发送 | 可发送 |
| 地址所有者修改/删除/管理港口 | 仅管理者 | 仅管理者 |

即：

> 私密地址不是“别人绝对寄不进去”，而是“系统不会主动告诉别人这个地址存在”。

这更接近现实中的地址和物流系统，也避免把“加入名单”误解成包裹投递协议的一部分。

### 3.1 管理权限仍然存在

“机制保护变成信息保密”不等于所有权消失。

仍应区分：

- 谁能重命名地址；
- 谁能切换公开 / 私密；
- 谁能删除地址；
- 谁能把新的远仓港加入该地址；
- 谁能调整该地址的其它管理设置。

但**知道准确地址名的人能否寄件**，首版不再由成员名单阻止。

现有 `owner / members / open / admits()` 需要在实施时重新拆分：
管理权限与“是否能作为订单目的地”不能继续共用一个判断。

## 4. 没有接收港地址的包裹：禁止发送并回退

普通 Create 包裹、损坏数据或异常流程可能把一个没有远仓目的地的包裹送进发送港。

固定行为：

```text
包裹进入发送港
    ↓
没有接收港地址
    ↓
禁止跨服发送
    ↓
记录 WARN / 报警
    ↓
转入回退面
    ↓
底部有漏斗/溜槽/容器 -> 退回本地物流
底部堵塞             -> 留在港内并持续报警
```

远仓港绝不使用“默认地址”猜测目的地，也绝不随机选择可用接收港地址。

这条规则同样适用于：

- 地址冲突；
- 地址已删除；
- 地址无法解析；
- 协议数据缺少必要路由字段。

不同故障可以有不同事件码，但保货策略一致。

### 4.1 2026-09-19 实施记录：物理回退闭环

已把“不要发送”从提示改成真实物料路径：

- 发送港遇到以下确定性路由错误时，不再把包裹长期卡在 outbound 槽：
  - 没有任何远仓路由；
  - 跨节点路由仍指向默认接收地址（等价于没有选择接收港地址）；
  - 接收港地址当前存在名称冲突；
- 包裹会原子地从 outbound 搬到港底部 fallback：先模拟 fallback 是否能完整接收，再从 outbound 取件，避免“退件失败反而丢件”；
- 底部存在漏斗 / 溜槽 / 容器时，现有 `drainFallback()` 自动把包裹交回本地物流；
- 底部没有可接收容器时，包裹保留在 fallback，港进入 `BLOCKED`，玩家与自动化仍可取回；
- 新增具体回退原因：无路由、未设置接收港地址、地址冲突；
- GameTest 增加“无接收地址 -> 自动退入下方箱子且港内无副本”的真实 tick 路径。

统一 Event Registry 的首版已经在 Phase C 落地：上述路由错误现在会产生可持久化、可 ACK / CLEAR 的 WARN；回退口堵塞也使用同一套事件状态。日志台方块与打印 ACK 仍属于 Phase D。

# 第二部分：统一事件与报警系统

## 5. 为什么需要统一事件系统

当前远仓已经有大量玩家真正需要知道的状态：

- Transerver 连接中断；
- 远仓港无目的地；
- 目标港满；
- 回退面堵塞；
- 包裹重试；
- Escrow / 隔离库异常；
- 互通塔停转、应力过载、以太不足；
- 请求失败；
- 接收港地址冲突；
- 仓储网络掉线或部分链接未加载。

这些信息不能继续分别藏在聊天、护目镜、日志和方块灯里。

应建立一套统一的 **Distant Stock Event / Alarm System**：
设备只产生事件，日志台、黄铜信号灯、蜂鸣器和监视器读取同一套状态。

---

## 6. 事件模型

建议首版事件至少包含：

```text
id              唯一事件 ID
createdAt       首次发生时间
updatedAt       最近更新时间
severity        DEBUG / INFO / WARN / ERROR
code            稳定事件码，例如 DOCK_NO_ADDRESS
sourceType      DOCK / TOWER / NETWORK / LINK / ORDER / ESCROW ...
sourceId        稳定设备或逻辑对象 ID（如有）
sourcePos       方块坐标（如有）
node            发生事件的服务器节点
summary         简短说明
active          故障条件当前是否仍存在
acknowledged    操作员是否已经确认
acknowledgedAt  确认时间
clearedAt       故障解除时间
count           同类事件重复发生次数
```

第一版不需要做成通用日志框架；只要稳定地支持远仓自己的事件即可。

### 6.1 等级

采用路由器/服务器日志习惯，同时映射到工业报警：

| 等级 | 含义 | 报警表现 |
|---|---|---|
| DEBUG | 开发诊断，默认不显示 | 无 |
| INFO | 正常操作记录 | 无报警；日志台正常绿灯 |
| WARN | 可继续运行，但需要注意 | 橙灯 |
| ERROR | 已影响物流或数据，需要人工处理 | 红灯 |

“FAULT”更适合作为事件类型/状态词，而不是再造第五套等级。

### 6.2 ACTIVE、ACK、CLEAR 三件事必须分开

报警状态：

```text
ACTIVE + 未确认
    -> 灯闪烁 + 蜂鸣器

ACTIVE + 已确认
    -> 灯常亮 + 蜂鸣器静音

CLEARED
    -> 报警灯熄灭，事件保留在历史中
```

**确认报警不等于修复故障。**

这条规则后面所有报警设备统一使用。

## 7. 远仓日志台

新增墙挂设备：**远仓日志台**。

视觉灵感来自现实中的火灾报警控制器 / 工业报警面板，而不是现代大触摸屏。

### 7.1 外观

建议元素：

- 墙挂矩形机箱；
- 小面积状态显示区；
- 两个辉光管 / 数码管式字符窗；
- POWER / WARN / ALARM 等小灯；
- 内置打印机构与窄纸出口；
- 少量机械按键；
- 避免大面积彩色 LCD。

两个字符窗可显示简单状态，例如：

```text
03   当前未确认事件数
W2   当前最高报警状态 / 分类
E7   错误码摘要
--   无报警
```

最终字符编码可在建模后再冻结。

### 7.2 日志浏览

日志类似路由器后台，可设置最低显示等级：

```text
DEBUG
INFO
WARN
ERROR
```

每条显示：

```text
[13:42:16] WARN  DOCK-03
NO RECEIVING ADDRESS
```

完整信息在界面里查看；方块本体只需要给出总状态和最近事件。

### 7.3 打印 = 操作员确认

日志台的“打印小票”不是纯装饰。

打印当前报警事件时：

1. 生成一张“远仓事件记录”纸条 / 小票；
2. 将该事件标记为 `acknowledged`；
3. 对应蜂鸣器停止；
4. 若故障仍然存在，对应橙/红灯由闪烁变为常亮；
5. 故障实际解除后灯才熄灭。

小票可包含：

```text
2026-09-19 13:42:16
远仓港 #03

WARN / DOCK_NO_ADDRESS
包裹缺少接收港地址
已转入回退出口

Event: DS-W-0142
```

打印只代表“操作员已经看到了”，绝不能把仍存在的故障直接清掉。

### 7.4 正常状态

没有活动 WARN / ERROR 时：

- POWER / NORMAL 绿灯常亮；
- 蜂鸣器静音；
- 字符窗显示正常状态或最近 INFO 计数。

## 8. 蜂鸣器

加入一组远仓工业蜂鸣器音效，风格参考工厂控制柜、地铁设备与工业报警器：
清晰、短促、足以引起注意，但不做成灾难警报或长时间高音量 siren。

首版将蜂鸣器作为**可复用报警声音行为**，供以下设备调用：

- 远仓日志台；
- 黄铜信号灯（独立放置模式）；
- 后续可能的其它报警设备。

不要求首版就增加独立“蜂鸣器方块”。如果后续确实需要红石蜂鸣器，再把同一套声音抽成独立设备。

建议至少准备：

- `warn`：橙色警告，较慢短鸣；
- `error`：红色报警，更明显的重复短鸣；
- `ack`：确认时很短的反馈音（可选）。

必须有冷却/节流，不能每 tick 播放。

## 9. 黄铜信号灯：远仓网络 Andon 灯

黄铜信号灯在独立放置模式下，应能直接绑定已有的 Create 仓储网络。

绑定后，它不再只是一个“输入多少就显示什么颜色”的灯，而是一个简化的网络 Andon 状态灯。

### 9.1 绑定

当前代码已经有：

- `SignalPanelBlock.lampBinding()`：可从已调谐远仓终端或 `LogisticallyLinkedBlockItem` 取得网络频率；
- `SignalPanelBlockEntity`：已经能保存 `lampNetworks` 并采样 `NetworkHealth`；
- `LampState` / `LampReadings`：已有一套黄铜灯的严重程度梯级。

因此后续不是重写黄铜灯，而是：

1. 确认**单独放置的一盏黄铜灯**完整复用这条绑定路径；
2. 将统一事件/报警系统的 WARN / ERROR 一并纳入黄铜灯的状态来源；
3. 增加可选蜂鸣器行为。

### 9.2 状态建议

```text
无绑定       熄灭 / 白色暗灯
正常         绿色
工作中       青色
WARN         橙色
ERROR        红色
```

未确认报警可闪烁；确认后若故障仍存在则常亮。

### 9.3 它与日志台的分工

黄铜信号灯回答：

> “哪里出事了？”

日志台回答：

> “出了什么事、什么时候发生、是否已经有人确认？”

工程师护目镜继续负责现场设备级详细诊断。

---

## 10. 监视器、日志台、黄铜灯不要重复实现故障判断

最终关系应为：

```text
远仓港 / 互通塔 / Transerver / 请求器 / Escrow / 仓储网络
                  ↓
             Event Registry
                  ↓
       ┌──────────┼──────────┐
       ↓          ↓          ↓
   远仓日志台   黄铜信号灯   监视器
       ↓          ↓
     打印 ACK    蜂鸣器
```

同一个 `DOCK_NO_ADDRESS` 不能在三个 UI 里各写一套判断。

# 第三部分：实施顺序

## 11. Phase A — 先修地址模型

优先级最高，因为它影响现有订单路由：

1. 玩家术语从“接收港组”迁移到“接收港地址”（语言工作线单独处理）；
2. `DockGroupDirectory.rename()` 补同一远仓网络内的重名拒绝；
3. 创建 / 重命名检查同一远仓网络内已知 `RemoteGroups` 同名；
4. `RemoteGroups.replaceFrom()` 检测同一远仓网络跨节点同名冲突；
5. 冲突地址不能被 `findByName()` 静默解析；
6. 新订单遇到冲突必须拒绝；
7. 增加 GameTest：本地重名、远端重名、断线后冲突恢复。

**这一阶段不必改 `DockGroup` 类名。** 先把行为改对，代码内部重命名以后再做。

### 11.1 2026-09-19 第一轮实施记录

已完成：

- `DockGroupDirectory.create()` / `rename()` 统一拒绝同名；
- 旧存档如果已经存在两个同名本地组，`findByName()` 不再取“第一个”，而是拒绝歧义；
- `RemoteGroups.findByName()` 不再从多个同名远端地址中任取一个；

## 12. Phase B — 公开 / 私密地址

### 12.1 2026-09-19 决策：采用 A / unlisted 模型

用户已拍板：**私密地址只是不公开（unlisted），不做密码学意义上的保密。**

因此：

- 私密地址名称仍随服务器公告同步到其它节点；
- 普通玩家的自动补全、地址浏览列表、港口公开读数中不显示私密地址；
- 知道准确地址名的玩家仍可手动输入并发送；
- 管理员、服务端日志、调试工具或修改过的客户端理论上仍可能看到私密地址名；
- 这不是访问控制，也不是安全边界，文案中应避免使用“加密”“不可见于服务器”等表述。

换句话说，它等价于“不列出”，而不是“隐藏于协议”。协议继续携带完整名称，避免为私密地址单独设计查询 / 哈希发现机制。

取三者最严重状态作为 Andon 输出。事件的 ACK 语义映射为：


### 13.3 基础设施报警生产者

已增加一秒一次的 `AlarmSampler`，只负责把真实基础设施状态投影成事件，不复制业务判断：

- `LINK_OFFLINE`：Transerver 曾经成功挂接后 transport down / API 消失时生成 ERROR；从未启用过 Transerver 的开发或单机环境不会产生假故障；恢复连接后 CLEAR；
- `TOWER_OVERSTRESSED`：完整互通塔所在 Create 动力网络过载时生成 ERROR；
- `TOWER_STOPPED`：塔已建成、未过载但无法正常运行时生成 ERROR；过载与普通停机互斥，只保留更准确的根因；
- `TOWER_NO_ETHER`：塔正在运行、确实带载设备、启用每包以太计费且当前余量不足支付一包时生成 ERROR；空闲塔或关闭计费时不报警；
- 塔拆除时主动 CLEAR 该塔已有事件；仅仅区块卸载不会把真实故障误判成恢复；
- 这些持续状态只在“进入故障”时 raise，一秒一次的采样不会把 `count` 当成持续秒数。

塔自身事件当前保持 tower/global scope，不随意绑定某张 Create 仓储网络；具体设备因塔故障无法工作时，设备级事件仍可携带自己的 `createFrequency`。这样全局日志台能看到基础设施故障，而绑定某仓库的黄铜灯不会因为一座不相关的塔停机一起变红。

## 16. 首批验收用例

### 地址

- A 已有 `工业区`，A 再创建 `工业区` -> 拒绝；
- A 已有 `工业区`，重命名其它地址为 `工业区` -> 拒绝；

- 冲突存在时下单 -> 拒绝且产生报警事件；
- B 改名后下一次公告 -> 冲突解除；
- 私密地址不出现在自动补全；
- 精确输入已知私密地址 -> 可以作为目的地。

### 无地址包裹

- 没有接收港地址的包裹进入发送港 -> 不发送；
- 回退口可用 -> 包裹从底部退出；
- 回退口堵塞 -> 包裹仍在港内，不丢失；
- 产生 WARN，解除堵塞后事件 CLEAR。

### 日志与报警

- WARN -> 橙灯闪 + 蜂鸣；
- ERROR -> 红灯闪 + 更高优先级蜂鸣；
- 打印事件 -> ACK，蜂鸣停止，故障未修复时灯常亮；
- 修复故障 -> CLEAR，灯熄灭；
- 同一持续故障不能每 tick 生成一条新日志；
- 历史记录达到上限后按规则淘汰，存档不能无限增长。

### 黄铜信号灯

- 单独放置的黄铜灯可绑定现有 Create 仓储网络；
- 网络正常 -> 绿色；
- 网络出现 WARN -> 橙色；
- 网络出现 ERROR -> 红色；
- 没有绑定 -> 不谎报“正常”；
- 未确认报警与已确认报警有明确闪烁差异。
