# 异构服务器物品传输与回退协议 V1

本文定义 Distant Stock 在各服务器模组列表、模组版本或注册表不同的情况下，如何传输 Create 包裹而不复制、不吞掉且可追回。Transerver 只保证消息的持久投递与最终回执；它不解释 Minecraft `ItemStack`。所有物品兼容性、世界落地和退件语义由 Distant Stock 负责。

## 不可破坏的约束

1. **单一保管方**：任意时刻必须能指出包裹由源端世界、源端托管箱、Transerver 持久消息或目标端收件箱中的哪一方负责；不得存在“双方都可取出”的状态。
2. **先持久化，后移动**：没有可靠写入下一保管方前，不得清除上一保管方的记录。
3. **最终确认才结算**：字节抵达 Router、目标节点或目标进程均不代表交付成功；只有目标服主线程把包裹插入指定远仓港后才返回 `APPLIED`。
4. **重试保持身份**：同一次发送的 `parcelId` 和 Transerver `messageId` 在所有重试中保持不变。
5. **拒收不降级**：未知物品、未知数据组件和不兼容版本不得被替换为空气、屏障、等价标签物品或删减后的 ItemStack。
6. **无法自动恢复就隔离**：达到重试上限、节点被删除或两端均无法解码时进入可见隔离库，绝不静默丢弃。

网络层只能提供至少一次投递。Distant Stock 通过持久托管、`parcelId` 幂等和目标端已应用记录，实现玩家可观察到的“实际一次”。

## 为什么不能只比较模组列表

- 两服可以安装许多互不相关的模组，但仍能安全传输原版石头；要求整份模组列表一致过于严格。
- 相同物品 ID 在不同模组版本中可能改变数据组件格式；只检查 `namespace:item` 过于宽松。
- 包裹内部可能包含容器物品、附魔、配方数据、流体、实体数据或模组自定义组件；顶层物品存在不代表内部数据可解码。
- 服务器可能在兼容性查询之后、实际送达之前更新整合包，因此预检结果只能作为提示，目标端落地验证才是最终裁决。

V1 按“本次载荷实际引用的注册表和模组”验证，不要求两服完整模组列表相同。

## 三层检查

### 1. 节点能力摘要

节点向 Transerver 目录登记：

- Minecraft 版本与 `DataVersion`；
- NeoForge/加载器版本；
- Distant Stock 物品协议版本范围；
- `registryEpoch`：每次服务器启动或数据包/注册表重载后改变；
- 模组 `modId -> version`；
- 管理员允许/拒绝策略摘要；
- 最大载荷、最大嵌套深度等限制。

该摘要用于请求器标记库存和发送前快速拒绝，不是最终凭证。

### 2. 发送前兼容性查询

源端根据准备发送的包裹生成 `PayloadManifest`，向目标节点查询。结果可按以下键短期缓存：

```text
destinationNodeId + registryEpoch + payloadFingerprint
```

目标端返回：

- `COMPATIBLE`：当前环境预计可接收；
- `INCOMPATIBLE(reason, path)`：确定无法接收；
- `UNKNOWN`：目标离线、版本未知或无法证明兼容。

默认策略下，`INCOMPATIBLE` 立即拒发；`UNKNOWN` 留在源端等待，不把风险转嫁给玩家。管理员可以选择允许离线排队，但包裹仍进入源端托管，不能直接消失。

### 3. 目标端权威落地验证

目标端收到 `package.dispatch` 后必须依次完成：

1. 校验协议版本、载荷长度和 SHA-256；
2. 校验目标 `nodeId`、收货港组、权限和策略；
3. 在解码前检查清单中的所有物品 ID 和相关注册表项是否存在；
4. 使用目标服 `RegistryAccess` 完整解码，保留 `DataResult` 错误，不允许把失败结果转为空栈继续处理；
5. 递归检查包裹内容、容器内容和自定义数据组件，限制深度、数量与总字节数；
6. 将解码结果重新生成语义清单，核对物品 ID、数量和组件哈希，防止未知内容被解码器静默丢弃；
7. 在服务器主线程中选择目标港并执行幂等插入；
8. 持久记录 `parcelId -> APPLIED` 后，才向 Transerver 返回 `APPLIED`。

任何永久不兼容返回 `REJECTED`；港满、区块未加载或设备暂时离线返回 `RETRY`。

## 载荷格式

`package.dispatch` 至少包含：

```text
schemaVersion
parcelId
correlationId
childOrderId
sourceNodeId
originDockGroupId
destinationNodeId
receivingDockGroupId
finalLocalAddress
minecraftDataVersion
distantStockProtocol
relevantMods[]          # 本载荷实际依赖的模组及版本
manifest[]              # 递归物品/组件清单
payloadFormat
payloadBytes
payloadSha256
```

`manifest` 是验证和 UI 信息，不是生成物品的来源；真正物品只能从通过哈希校验的 `payloadBytes` 解码。Transerver 将载荷视为不透明字节，不尝试转换物品。

## 源端托管，而不是“先删再发”

源端远仓港必须拥有持久 `EscrowRecord`：

```text
parcelId
sourceDock
originDockGroupId
exactPayloadBytes
payloadSha256
destination
state
messageId
lastResult
```

发送步骤：

1. 包裹进入发送港，仍由方块库存持有。
2. 完成快速兼容性查询；确定不兼容时保持原槽位并显示原因。
3. 将完整载荷和路线原子写入源端托管记录。
4. 锁定/清空可见槽位，使玩家不能同时取走原包裹；此时托管记录成为唯一权威副本。
5. 使用固定 `messageId` 写入 Transerver outbox。写入失败则从托管记录恢复原槽位。
6. 在收到最终回执前，托管记录不可被玩家取出、删除或再次发送。
7. 收到 `APPLIED` 后删除托管记录并结算成功；收到 `REJECTED` 后由托管记录恢复原包裹。

因此，目标端拒收时通常不需要把物品字节再“传回来”：源端一直保留不可见、不可重复领取的权威托管副本。这样比让不兼容目标服重新编码退件更可靠。

## 拒收与退件

### 发送前拒绝

- 包裹保持在发送港；
- 不消耗以太凝液；
- 红色状态灯和护目镜显示具体原因；
- 玩家可从退件面取回或修改目标后重试。

### 发送后收到 `REJECTED`

- Transerver 持久保存最终回执和原始已发送载荷；
- 源端根据 `parcelId` 找到托管记录；
- 若来源港存在且有空间，恢复原包裹；
- 若来源港不可用，放入该服务器的持久退件箱，等待任意同组远仓港认领；
- 恢复成功后才确认并清理 Transerver 的 completed send。

### 来源服更新后也无法解码

托管记录保留原始字节并进入 `QUARANTINED`。管理员可以在恢复旧模组后重试，或导出原始载荷和清单。不得尝试构造缺组件的残缺物品。

## 崩溃与网络异常矩阵

| 故障时刻 | 恢复行为 |
|---|---|
| 写托管记录前崩溃 | 包裹仍在方块库存 |
| 托管已写、outbox 未写时崩溃 | 重启后继续写 outbox，或安全恢复原槽位 |
| Router 收到但目标离线 | Router 持久保管并重试，源端托管不释放 |
| 目标插入后、回执发送前崩溃 | 相同 `messageId` 重投；目标端根据 `parcelId` 返回既有 `APPLIED`，不再插入 |
| 源端收到 `APPLIED` 前崩溃 | 重启后从 Transerver completed send 重放结算并删除托管 |
| 目标端模组在排队时改变 | 权威落地验证失败，返回 `REJECTED`，源端恢复托管包裹 |
| 来源节点长期离线 | Router 和源端磁盘记录继续保留，不转投其它服务器 |
| 节点身份被管理员删除 | 消息进入 dead-letter；源端恢复或隔离托管包裹 |

## 防复制要求

- 目标端必须持久保存已应用 `parcelId`，保存期不能短于 Transerver 的消息和回执保留期。
- 同一 `parcelId` 若载荷哈希不同，视为协议攻击或严重损坏，直接隔离并报警。
- `APPLIED` 表示物品已进入目标港，之后即使玩家马上取走，也不能因消息重试再次生成。
- `REJECTED` 一旦成为最终结果，目标端不得在后台继续落地同一包裹。
- 管理员“强制重试”必须产生新的发送尝试 ID，但继续引用同一个托管对象，并留下审计记录。

## 默认兼容策略

V1 默认值：

- Minecraft 版本必须完全相同；
- Distant Stock 物品协议版本必须有交集；
- 原版物品仍需通过完整组件解码与语义清单核对；
- 模组物品要求目标服存在同 ID，来源模组版本默认完全相同；
- 任意未知数据组件、缺失注册表项或静默丢失均拒收；
- 不根据物品标签自动替换，例如不把某模组铜锭改成另一模组铜锭；
- 禁止嵌套远仓包裹，直到循环和尺寸规则经过单独设计；
- 超过最大载荷或嵌套深度的包裹拒收并原地退件。

以后可通过公开接口注册显式适配器，例如：

```text
ItemTransferCompatibilityProvider
  inspect(manifest, targetCapabilities)
  validateDecoded(stack, sourceManifest)
  optionalConvert(stack, declaredRule)
```

适配器必须由物品所属模组或管理员明确启用，声明输入、输出和版本范围；核心协议不能写死特定模组，也不能把“看起来相似”当作兼容。

## 请求器体验

远程库存条目按当前收货服务器显示：

- 正常：可下单；
- 黄色：目标离线，兼容性未知；
- 红色：确定不兼容，不允许加入订单；
- 信息提示示例：`目标服务器缺少 createaddition:electric_motor`；
- 一份订单包含不兼容物品时，只拒绝对应行，不先生产再退件。

管理员监视器至少显示：待预检、托管中、运输中、退件、隔离和最后错误。玩家必须能通过 `parcelId` 查询一次传输的当前保管方。

## 与 Transerver 的边界

Transerver 已提供：

- 固定 `messageId` 的持久 outbox/inbox；
- Router 中继存储；
- `APPLIED / RETRY / REJECTED` 应用回执；
- completed send 与 dead-letter；
- 消息去重、哈希和最大载荷限制。

Distant Stock 必须新增：

- `PayloadManifest` 与节点能力频道；
- 目标端完整 ItemStack 验证器；
- 源端 `EscrowRecord` 持久托管；
- 目标端 `parcelId` 已应用账本；
- 最终回执后的恢复、结算和隔离处理；
- 请求器兼容性标记与管理员诊断 UI。

旧的临时 HTTP `/package` 路径只能用于开发验证，不能作为正式物品运输路径。

## 发布前必须通过的测试

1. 两服模组完全相同，正常包裹只落地一次。
2. 目标服缺少顶层物品所属模组，源端原包裹可立即取回。
3. 顶层物品存在但自定义数据组件缺失，拒收且内容不变。
4. 包裹含混合兼容/不兼容物品，整包拒收，不进行部分落地。
5. 目标港满、卸载、重载和服务器重启后继续投递。
6. 目标落地后故意丢弃回执，重复消息不生成第二份包裹。
7. 源端写托管、写 outbox、收到回执和恢复退件的每个间隙强制崩溃。
8. 排队过程中卸载目标模组，恢复后拒收并退回来源。
9. 来源服也卸载模组，退件进入隔离库且原始字节可导出。
10. 篡改 `parcelId`、载荷哈希、目标港组、数量和嵌套深度，均安全拒绝。
11. 两服只存在无关模组差异，原版物品仍可正常传输。
12. 一百次重复提交、断线和乱序回执后，源端与目标端的物品总数保持守恒。
