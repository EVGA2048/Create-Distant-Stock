# 远仓权限模型提案（待商讨）

ROUTING-V1 第 3 条要的是「公开 / 指定服务器共享 / **配对码**（一次性、限时）」。
现在只有最粗的一档：港组有 owner，加一个 open 开关。这份文档把它拆成能落地的结构。

## 一、现状：一个布尔值，一个判定位

`DockGroup(id, name, owner, open)`，判定只有一个方法：

```java
public boolean admits(UUID player) {
    if (open || owner == null) return true;   // 公开组 / 无主组（旧的、命令建的）
    return owner.equals(player);
}
```

**好消息是判定位只有一个。** 全仓库只有四处问权限，全部走 `admits`：

| 调用点 | 问的问题 |
|---|---|
| `PlaceOrderC2S:76` | 这个人能不能往这个组下单 |
| `DockBlock:275` | 这个人能不能把这台设备指着这个组 |
| `DockGroupsS2C:93` | 这个组的名字/归属要不要发给他 |
| `RequesterMenu:178` | 界面里这一项能不能选 |

所以**权限模型扩的是 `DockGroup` 和它旁边的一张表，不是四条路径**。这是这份提案能小的唯一原因。

## 二、三个真实的问句

玩家嘴里的「权限」其实是三个不同的问题，混在一起会做出一套谁都看不懂的界面：

1. **谁能把货送进我的组？** —— 别人下单，货从我港里出来。**这是最要紧的一条**：它决定谁能占用我的港、
   谁能在我的工厂里刷出东西。
2. **谁能往我的组里加港？** —— 谁能扩张这套系统。今天和 1 绑在同一个 `admits` 上，应该分开：
   「能给我送货的人」和「能改我系统的人」不是一批人。
3. **谁能看见我的组存在？** —— 选组列表里出现哪些组。今天 `DockGroupsS2C` 一次把全服所有组发给你，
   名字、归属、港数量全都有。**这一条现在完全没有。**

## 三、提案：把 open 换成一个三档策略

```java
public enum Access {
    PRIVATE,    // 只有成员表里的人（owner 永远是成员）
    PUBLIC,     // 任何玩家（＝今天的 open = true）
    SHARED      // 只有成员表里的人，但成员表由 owner 手工维护（＝白名单，与 PRIVATE 的差别见下）
}
```

`DockGroup` 增加两个字段：

```java
record DockGroup(UUID id, String name, UUID owner, Access access,
                 Set<UUID> senders,   // 谁可以把货送进来（问句 1）
                 Set<UUID> builders)  // 谁可以往组里加港 / 改名（问句 2）
{ }
```

判定拆成两个方法，**`admits` 保留为 `canSend`，语义不变**（少改调用点）：

```java
boolean canSend(UUID player)   // owner || access == PUBLIC || senders.contains(player)
boolean canBuild(UUID player)  // owner || builders.contains(player)
```

今天的世界升级上来：`open == true` → `Access.PUBLIC`，`open == false` → `Access.PRIVATE`，两张表空。
**存档向后兼容不需要写迁移代码**——`read` 里 `hasUUID`/缺键回落到旧字段即可（这条踩过坑：`getUUID` 缺键返回 null，
`putUUID(key, null)` 会 NPE）。

### 三个档位的真实差别（避免做出两个一样的档）

- `PRIVATE`：成员表**只能通过配对码加人**（一手交码一手交人，见第四节），owner 不能手输 UUID ——
  玩家没有地方查别人的 UUID，做一个填 UUID 的框等于做一个坏掉的框。
- `SHARED`：在 `PRIVATE` 的基础上多一个**从服务器玩家列表里勾人**的界面。单人存档里这一档没有意义，
  它是给互相信任的小团体用的（「我这个组的货可以从他那出来，但他不能改我的组」）。
- `PUBLIC`：任何人不经同意就能送货。**默认应该是 PRIVATE**，`PUBLIC` 是玩家主动打开的。

## 四、配对码：这一条才是「跨服」的关键

跨服场景下你**没法查对面服务器的玩家列表**——两台服务器的 UUID 空间和在线名单互不可见。
所以「勾人」的界面在跨服那一侧根本做不出来。配对码不是锦上添花，它是跨服唯一可行的授权方式。

```java
record PairingCode(String code, UUID group, UUID issuer,
                   long expiresAt, int usesLeft, boolean crossServer) { }
```

规则（每条都对着一个具体的坑）：

| 规则 | 为什么 |
|---|---|
| **一次性**：兑换成功就 `usesLeft--`，到 0 删除 | 码会被截图、会被贴在聊天里。能重复用的码等于公开组。 |
| **限时**：默认 10 分钟，上限 1 小时 | 同上，而且它让「过期要重发」这件事变成预期行为，玩家不会觉得是 bug。 |
| **短**：6 位，去掉 `0/O/1/I` | 手抄的码。跨服场景下玩家是在聊天框里打字。 |
| **兑换是双向的**：A 生成码 → B 兑换 → **B 的组/网络出现在 A 的成员表里，A 也在 B 的成员表里** | 「我允许他送货」和「我可以给他送货」在跨服里几乎总是一起要的。只做单向会让玩家生成两个码。做成双向要明说。 |
| **生成者是 owner** | 与被授权的人不是 owner：码授的是**使用权**，不是所有权。 |
| **撤销即时**：owner 从成员表删人 | 但**已经在途的包裹照落**——承诺已经做出去了，在别人服务器上没法撤回。新订单一律拒。这条要在护目镜/界面上写出来，否则玩家会以为撤销没生效。 |
| **码不落存档**（可选） | 服务器重启时未兑换的码全部作废，是更安全的默认，但会打断「约好明天一起玩」。**建议落存档**，靠过期时间兜底。 |

码存在 `PairingCodes`（`SavedData`，照 `DockGroupDirectory` 的形状写），键是码本身。
兑换走一个 C2S 包（`RedeemCodeC2S`），成功后回一个 `DockGroupsS2C` 刷新列表。

## 五、跨服那一侧要多传什么

跨服订单是**两台服务器各自记账**，所以权限必须在**两边**都成立，而且是用各自本地的表判定：

- 发送侧的检查：「我有没有权利从**那个网络**取货」——发送方本地的表。
- 接收侧的检查：「这批货有没有权利落在**我的组**里」——接收方本地的表。

今天 `OrderService.place` 只查了发送侧。**接收侧的检查在货到达时才做**，也就是说
**货已经跨过去了才被拒**——不能退回去（对面不确定还在不在），只能走回退面。
这是可以接受的，但要在监视器上把「因权限被拒」和「因为没地方放」分开报，
否则玩家看到一堆退货包裹不知道是网络断了还是自己被踢了。

跨服码建议带一个**网络指纹**（`RemoteNetworkId` 的短标签），兑换时对不上就直接拒——
防止码被贴到公开频道后被不相关的人兑走。这不是安全边界，是防手滑。

## 六、不做什么（明确划掉）

- **不做队伍/权限组系统。** 那是 FTB Teams 那一层的事。要和它联动就写一个适配器：
  `FTBTeams` 在线时把 `canSend` 桥到队伍成员表。**这应该是另一个决定，不是这个模型的一部分。**
- **不做逐港权限。** 权限挂在组上，港跟着组走。逐港权限会让「这个组的货从哪个港出来」
  变成一个需要逐个港配置的问题，而轮转逻辑（组内轮转）会立刻和它打架。
- **不做公开网络浏览。** 「服务器里有哪些网络」不应该是可浏览的。跨服靠码，同服靠勾人。

## 七、落地顺序（每一步都能单独试）

1. `Access` + 两张成员表 + `canSend`/`canBuild` 拆分。旧字段读回兼容，**不动任何界面**。
2. 组设置界面：三档选择器 + `SHARED` 的勾人列表（用 `DockGroupsS2C` 已有的玩家名来源）。
3. `PairingCodes` + 生成/兑换包 + 界面上一行「输入配对码」。
4. 接收侧权限检查 + 监视器上把「权限拒收」独立成一类告警。
5. （可选）FTB Teams 桥。

## 八、要你定的事

1. 默认档位：新组默认 `PRIVATE` 还是 `PUBLIC`？（建议 PRIVATE）
2. 配对码要不要**双向**？（建议双向，界面上要写清楚）
3. 配对码要不要落存档？（建议落，靠过期兜底）
4. `SHARED` 这一档要不要？单人存档没意义，但服里「信得过的三个人」用得着。
5. 撤销后在途包裹照落——同意吗？（技术上没得选，但要你确认这是你能接受的规则）
