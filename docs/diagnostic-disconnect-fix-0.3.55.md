# 0.3.55 诊断蛙港断路漏检修复

## 根因

原实现每轮从当前连通图重新生成接收地址列表，并覆盖已知地址。等待发包时断开分支后，目标被直接移出下一轮；等待回包时断开，则超时处理无法再取得原接收蛙港，缓存接管和恢复目标也可能丢失。

## 修复

诊断蛙港保存已发现的「方块位置 → 业务地址」名单，写入世界 NBT。轮询、超时和未接管状态的恢复探测统一读取这份名单。断路和区块未加载不会删除记录；只有加载后确认拆除、改址或关闭收包，才退出旧地址的检测。未加载目标不会被诊断逻辑强制加载。拆除诊断蛙港时清理对应的运行时地址摘要。

同址多接收点仍遵循 Create 的地址语义：正常探测允许任意同址接收点响应；缓存接管后逐个通过私有地址恢复。

旧存档兼容：没有 KnownReceivers 字段时从空名单开始发现。升级前已经断开的分支必须先接回一次；新版无法凭空知道从未观察过的蛙港位置。

## 验证

- 原调度代码 + 新回归用例：`disconnectedReceiverSurvivesNextScanAndRecovers` 在断路后的下一轮检查失败，提示目标从名单消失。
- 修复后 `./gradlew -PwithGameTests runGameTestServer`：281 项必需测试全部通过。
- 新增用例覆盖发包前断路、等待回包时断路、超时告警、缓存接管、恢复解冻、名单 NBT 重载、改址、只发送、拆除、未加载区块及已撤销地址的迟到超时。

## Tomori 实机复测

1. 安装 0.3.55，让所有分支连通并被诊断蛙港发现。
2. 在等待下一次发包时切断一条分支：该地址应继续检测并最终报超时，不能静默消失。
3. 在 Ping 发出后、回包前切断分支：有可用缓存蛙港时应接管原业务地址；重新连接后，恢复 Ping 应解除故障和接管。
4. 断路状态保存退出，再进入世界：名单应保留并重新探测；拆除或修改接收蛙港地址后，旧地址不应留下永久告警。

以上自动测试使用本机 Create 6.0.10 / NeoForge 21.1.231；Tomori 的实际服务器场景仍需复测确认。
