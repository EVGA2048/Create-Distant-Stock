# 机械动力：远仓——当前项目审查与改进建议

> 审查日期：2026-09-17  
> 面向对象：DistantStock 与 Transerver 的开发者、设计参与者  
> 文档性质：阶段性技术与玩法审查，不替代最终设计规范

## 一、结论先行

目前的“机械动力：远仓”已经拥有一套相当扎实的跨服可靠运输基础：稳定节点标识、包裹实体化、路由、托管、幂等、回执、退件、隔离以及模组差异处理等关键问题，都已经被认真考虑并实现了相当一部分。

当前最大的风险已经不再是“跨服能不能传”，而是以下四层尚未完全收束：

1. **玩法规则层**：互通塔究竟是硬性前置、性能增益，还是二者混合，目前设计与代码存在矛盾。
2. **权限与网关层**：服务器、玩家、物流网络和收货港组之间缺少可撤销、可审计的授权边界。
3. **交互反馈层**：玩家能提交请求，但不容易判断订单最终是已打包、运输中、已送达，还是失败、退回。
4. **工程发布层**：DistantStock 仍依赖本地路径和未正式版本化的 Transerver 构建，发布流程不可复现。

因此，建议暂时停止继续扩张世界互通塔和外围设备，先把“普通互通塔 + 远仓港网关 + 请求生命周期 + 权限模型 + 可复现构建”收束成一个稳定闭环。

推荐实施顺序为：

> 提交并版本化 Transerver → 重做授权与网关边界 → 冻结互通塔规则 → 补齐订单最终状态回传 → 清理文档与发布构建 → 再开发世界互通塔

## 二、当前方案中做得很好的部分

### 2.1 使用稳定标识，而不是把 IP 地址写进包裹

节点使用稳定的 `nodeId`，服务器地址仅作为可变连接信息。这能够避免服务器迁移、域名更换或 ZeroTier 地址变化后，世界中已有包裹全部失效。

这一点应继续坚持：

- 包裹保存逻辑目的地，而不是实际网络地址；
- Transerver 根据节点标识查询当前连接地址；
- 地址变化不改变包裹的语义；
- 玩家界面显示服务器别名，不暴露 IP。

### 2.2 远仓港不是“一对一跨服箱子”

远仓港作为本地物流网络的出入口，包裹自身携带目的信息，Transerver 负责跨节点转运。这个模型比 ESLink 式固定成对容器更适合多服务器、多网络、多港组场景。

它自然支持：

- 一台服务器连接多个服务器；
- 一个服务器存在多个物流网络；
- 一个网络拥有多个远仓港；
- 一个收货港组包含多个远仓港；
- 港口可以按可用性和负载进行选择，而不是写死坐标。

### 2.3 可靠运输的底层方向正确

当前项目已经具备或规划了以下可靠性机制：

- 包裹标识与幂等处理；
- 发送托管，避免发送后直接丢失；
- 回执和重试；
- 失败退回；
- 无法解码物品的剥离、退件或隔离；
- 收发双方模组列表不一致时的兼容检查；
- 防止同一包裹被重复领取。

这是远仓区别于“能跑的演示程序”的核心价值，应当优先保护，不能为了快速增加玩法而绕开这些路径。

### 2.4 美术语言已经逐渐形成统一体系

目前确定的白灰、淡蓝、以太晶体、安山岩结构件、Create 小灯与机械框架已经具备辨识度。远仓港、远仓打包机、远仓机壳、请求器和互通塔开始像同一套设备，而不是彼此独立的方块。

后续不宜再频繁推翻主题色。更适合把精力放在：

- 方块拼接纹理；
- 动画遮挡和穿模；
- 激活、故障、离线状态的统一颜色语义；
- 物品图标与方块模型在游戏光照下的实际表现。

## 三、必须优先解决的问题

## 3.1 构建和发布目前不可复现

DistantStock 的构建脚本仍包含本机模组包的绝对路径，并依赖相邻目录中 Transerver 的 `0.1.0-SNAPSHOT` JAR。这样会产生几个问题：

- 换一台电脑后无法直接构建；
- 无法确认发布包究竟对应 Transerver 的哪次源码；
- 本地未提交改动可能被悄悄打进 DistantStock；
- CI、Modrinth 和 CurseForge 的发布流水线无法可靠复现。

审查时，Transerver 工作区仍存在多处未提交 Java 与测试改动，而 DistantStock 已经读取其中新增的 `knownNodes()` 行为。这意味着两个仓库当前并没有形成清晰、可追溯的版本组合。

### 建议

1. 先整理、测试并提交 Transerver 当前改动；
2. 为 Transerver 建立正式版本号和 Git 标签；
3. DistantStock 依赖明确版本，而不是长期依赖 `SNAPSHOT`；
4. 删除构建脚本中的个人绝对路径，改为 Gradle 属性或开发环境配置；
5. 后续可选择 Maven 本地仓库、私有 Maven、GitHub Packages 或 Gradle composite build；
6. 在发布记录中明确 DistantStock 与 Transerver 的兼容版本范围。

这是发布到 MCMOD、Modrinth 和 CurseForge 之前的最高优先级事项。

## 3.2 跨服授权目前以“服务器已知”为主，而不是“玩家被授权”

当前网络公告会周期性地把本地可见网络发布给已知节点；配对码兑换后，远程港组也更接近服务器级全局记录。订单请求中含有网络、港组、地址和物品等信息，但缺少明确的玩家、团队或授权凭证。

这会产生一个关键问题：

> 某位玩家完成配对后，同服务器上的其他玩家是否也自动拥有该远程网络的查看和下单权限？

如果答案是“是”，小型互信服务器可能可以接受；但如果模组面向公开服、阵营服或多人共建服，这个边界不够安全，也难以撤销和审计。

### 建议：引入可撤销的授权凭证

可以引入 `grantId`，由网络所有者或管理员签发，至少包含：

- 来源节点；
- 可访问的物流网络；
- 可使用的接收港组；
- 被授权玩家、团队或服务器主体；
- 权限集合，例如查看库存、提交请求、投递包裹；
- 有效期；
- 撤销状态。

订单与网络查询携带 `grantId`，目的端执行最终校验。配对码只是生成授权的临时入口，不应本身成为永久权限。

同时建议预留 `AccessPolicyProvider` 一类接口，未来可接入：

- 原版白名单或 OP；
- LuckPerms；
- FTB Teams；
- 服务器自定义账户系统；
- 世界互通塔的公共授权规则。

## 3.3 远仓港应成为物流网络的真正网关

目前最适合的长期模型是：

> 只有至少一个已绑定的远仓港存在时，该 Create 物流网络才对远端可发现、可查询、可请求。

远仓港因此同时承担三项职责：

1. 本地物流网络与跨服系统之间的物理出入口；
2. 网络库存和能力的公告网关；
3. 收发包裹的执行端。

这也解决了现有工厂改造成本问题：玩家无需把全厂所有原版打包机更换为远仓打包机，只要在既有网络中新增一个远仓港，即可让该网络具备远仓能力。

远仓打包机仍然可以保留，但定位应是：

- 主题一致的便捷方块；
- 可直接生成远仓包裹的专用设备；
- 新建工厂的推荐方案；
- 不是接入远仓系统的唯一方案。

文档中“只有远仓打包机才能参与远仓”的表述需要修正，否则会与现有路由能力和“低改造成本”的目标冲突。

## 3.4 互通塔当前存在可绕过的规则矛盾

当前激活逻辑存在一个明显反直觉行为：

- 当一个维度没有运行中的互通塔时，远仓设备可以免费工作；
- 一旦建成并运行第一座塔，设备才开始受到范围限制；
- 如果关闭或破坏最后一座塔，设备又恢复免费工作。

这意味着玩家可以通过不造塔或停掉塔来绕过范围、应力和以太消耗，互通塔反而像一种惩罚。

### 应在两种设计中明确选择一种

#### 方案 A：硬性前置，推荐

- 没有互通塔，远仓设备不工作；
- 塔决定激活范围、设备带载量和区块加载；
- 塔的等级提升范围、吞吐和效率；
- 世界互通塔是后期的全球基础设施。

优点是玩法目标清晰，能够支撑完整科技树。

#### 方案 B：软性增益

- 没有塔时设备仍能工作，但速度慢、成本高、无区块加载；
- 有塔后获得范围内加速、降低燃料消耗、提高并发和可靠性；
- 塔不是许可开关，而是性能设施。

优点是对旧存档和低需求玩家更友好。

不建议保留当前“无塔免费、有塔受限”的混合规则。若采用硬性前置，可以为旧世界提供一次迁移宽限期或配置项。

### 互通塔还存在两项具体技术问题

1. 区块加载逻辑需要检查塔是否真正处于运行状态，不能仅凭塔存在和等级持续加载区块；
2. 自动加载的方形区域也应计入全局区块上限，否则可能绕过管理员配置的容量限制。

另外，塔扫描逻辑虽然构建了流量统计映射，但返回扫描结果时没有把该映射传回，可能导致塔的流量显示长期为零。这是一个较明确的实现缺陷，应单独修复并补测试。

## 3.5 以太消耗的默认值与文档存在冲突

配置注释、设计文档与实际默认值对“每个包裹是否消耗以太”存在不一致。实际代码中相关开关默认为开启，而部分说明仍将其描述为关闭或未定。

这会直接影响玩家对互通塔、远仓港和流体生产线的理解，必须在首个公开版本前统一。

还需要进行一次实际吞吐量测试。目前设想的 `250 mB/包裹` 等于一份以太石英工序对应的完整单位，若自动化工厂持续发包，成本可能过高。建议通过真实物流压力测试确定：

- 每包固定消耗；
- 按物品数量消耗；
- 按跨服距离或塔等级消耗；
- 发送端、接收端或双方分别承担；
- 塔是否提供效率减免。

## 四、玩家交互需要进一步简化

## 4.1 “接收港组”同时表达两个概念，容易混淆

当前同一个接收港组字段可能表示：

- 本服港组：货物从远端取出后送回请求者所在服务器；
- 远端港组：货物在货源服务器内部送到另一个网络或位置。

这对开发者可以解释，但玩家不容易在下单时建立稳定直觉。

### 建议界面先选择交付方向

第一步明确：

- **送回本服**；
- **留在货源服**。

第二步再只显示对应一侧可选的接收港组。

同时将两个地址字段改为更明确的名称：

- `货源侧取件地址`；
- `收货侧分拣地址`。

提交前显示完整路线预览，例如：

> 从「仓库服 · 主仓网络」取货 → 送至「生存服 · 中央收货港」

这样玩家不需要理解底层节点、网络 ID 和路由表。

## 4.2 所有请求设备应共享同一份请求配置模型

手动远仓请求器、便携式请求器、远仓仪表和红石自动请求器目前对地址、港组和通配规则的支持并不完全一致。

建议抽象统一的 `RequestProfile`，至少包含：

- 货源节点与网络；
- 交付方向；
- 接收港组；
- 货源侧取件地址；
- 收货侧分拣地址；
- 物品过滤与数量；
- 授权凭证；
- 缺货时策略；
- 重试与冷却策略。

各设备只负责提供不同的交互方式，不应各自实现一套不兼容的下单语义。

## 4.3 “已加入队列”不等于订单完成

目前请求器显示的成功更接近“消息已发给 Transerver”，不代表货物已经：

- 被货源网络接受；
- 完成打包；
- 进入跨服运输；
- 到达接收港；
- 被本地物流网络收走。

如果中途缺货、没有互通塔、以太不足、权限失效、目的港已满或物品不兼容，玩家缺少最终反馈。

### 建议建立统一订单生命周期

至少包含：

1. 已提交；
2. 已接受；
3. 打包中；
4. 运输中；
5. 已到达；
6. 已完成；
7. 已拒绝；
8. 已退回；
9. 需管理员处理。

失败原因应机器可读并可本地化，例如：

- 库存不足；
- 网络离线；
- 无运行中的互通塔；
- 以太不足；
- 超出带载量；
- 授权已撤销；
- 目的港无空间；
- 目标服务器缺少对应物品；
- 包裹已进入隔离区。

代码中已经预留订单结果通道，但还没有形成完整的最终结果闭环。建议优先完成它，再继续扩展更多自动请求设备。

## 五、长期运行与数据清理风险

### 5.1 入站订单与路由记录缺少明确回收机制

入站订单收件箱和订单路由目录目前更偏向不断追加。路由目录虽然有限额，但若某些订单永远没有形成包裹、包裹丢失或流程中断，记录可能长期保留，最终达到上限并拒绝新的路由订单。

### 建议

- 为订单、路由、托管和回执设计统一保留期限；
- 完成、退回、取消后写入短期墓碑记录，防止重复处理；
- 墓碑过期后再安全清理；
- 对长期未完成订单提供管理员查询和取消命令；
- 接近容量上限时输出明显告警；
- Transerver 与 DistantStock 对同一状态的保留时间需要协调，不能一端先删掉恢复所需记录。

### 5.2 多世界支持需要显式进入标识与权限模型

服务器中可能存在 Multiverse 或其他多世界插件。节点标识不能只定位到服务器，物流网络和港口至少还需要稳定地区分：

- 维度；
- 世界实例；
- 物流网络；
- 港组。

世界被重命名、复制或重建时，也要明确哪些标识保持不变。区块加载和互通塔范围必须绑定正确世界，不能因为维度键相同而串联不同世界实例。

## 六、不同模组列表的兼容性

当前方向是合理的：包裹携带清单，目的端执行最终解码；不兼容条目可以剥离、退回或隔离，并限制重复往返次数。

仍需注意，Minecraft 物品并不总是简单的 `物品 ID + 数量`。一些模组会把重要数据放在：

- Data Components；
- 自定义 NBT；
- 嵌套容器；
- 模组自定义序列化结构；
- 绑定玩家或世界的对象引用。

因此，“发送前检查注册表”只能作为预检，目的端真实解码结果才是最终判断。

### 建议

1. 提供物品兼容扩展接口，让其他模组注册验证器或转换器；
2. 默认拒绝无法安全重建的物品，不做猜测性降级；
3. 保留原始清单和失败原因，方便管理员恢复；
4. 建立真实的混合模组测试矩阵，而不只测试双方完全相同的开发环境；
5. 覆盖潜影盒、背包、蓝图、装有流体的容器、带附魔和自定义组件的物品。

## 七、内容设计与范围控制

### 7.1 明确前期与中后期定位

远仓港和请求器的合成成本较低，而互通塔和以太生产链明显更偏中后期。如果互通塔是硬性前置，应在配方和 JEI/Ponder 引导中让玩家清楚看到完整解锁路径。

可以形成三阶段：

1. **本地准备**：远仓机壳、远仓打包机、远仓包裹、基础港口；
2. **跨服启用**：普通互通塔、应力输入、以太流体、网络授权；
3. **大型基础设施**：高等级塔、区块加载、共享吞吐、世界互通塔。

### 7.2 暂缓世界互通塔

世界互通塔的概念很好，但它会同时扩大以下问题：

- 谁拥有和管理；
- 谁提供燃料；
- 哪些玩家可使用；
- 全球设备如何计费；
- 多世界如何生效；
- 停机时如何回退；
- 是否形成单点故障；
- 公共服务器如何防滥用。

这些问题都依赖普通互通塔和授权模型先稳定。因此建议先保留美术和概念文档，不立即进入正式程序实现。

### 7.3 信号灯系统暂时冻结扩张

安山信号灯、黄铜信号灯和灯信链接器很有 Create 风味，也有独立发布潜力，但它们不是跨服运输闭环的必要条件。

当前阶段建议只修复已有功能和兼容工厂仪表，不继续增加新的灯型、旋转警示灯或复杂逻辑，以免主线再次被分散。

## 八、代码结构与文档维护

### 8.1 若干类已经过大

以下类承担的职责较多，后续修改容易相互影响：

- `RequesterScreen`；
- `RequesterMenu`；
- `DockBlockEntity`；
- `DockBlock`；
- `AdminCommand`。

建议逐步拆分为：

- 请求配置与校验；
- 路由预览；
- 网络发现；
- 港口库存与动画；
- 包裹发送状态机；
- 管理员诊断子命令。

不建议为了“重构整洁”一次性重写；应在补测试后按功能边界逐步抽取。

### 8.2 文档已经出现版本漂移

README、项目总览、设计文档、交接文档和游戏内教程之间存在互相矛盾的说法，例如：

- 无塔时设备是否可用；
- 每包是否默认消耗以太；
- 是否必须使用远仓打包机；
- 请求器是否已经实现双地址；
- 远仓港承担网关还是单纯收发容器。

建议建立一份唯一的“当前规范”，其他旧交接文档明确标记为历史资料。每次功能规则变化，只更新当前规范、测试和游戏内教程，避免把聊天结论散落在多个文件中。

## 十一、最终判断

远仓目前最有价值的不是新增了多少方块，而是它已经逐渐形成一种不同于 ESLink 的结构：

> 玩家建设真实的 Create 物流网络，包裹携带逻辑目的信息，远仓港把本地网络接入可靠的跨服运输层，互通塔提供世界内的基础设施与成本，Transerver 只负责可信地转运而不替玩家决定工厂结构。

这个方向是成立的，也值得继续做。

下一阶段不应继续堆叠概念，而应把已有概念之间的边界做清楚：谁能看见网络、谁能请求物品、哪个港口负责出入、塔在什么条件下生效、订单最后发生了什么、故障后如何恢复。只要这几件事完成，远仓就会从“功能很多的开发版本”真正变成“玩家能够理解、管理员敢于长期运行的模组”。
