# 机械动力：远仓——程序实施计划

> 更新日期：2026-09-10  
> 目标版本：先完成可靠的多服包裹传输，再扩展互通塔与材料系统。

## 交互约束

远仓遵循 Create 的交互习惯：

- 远仓港不使用全屏管理界面；
- 工作模式、优先级等少量数值使用右键按住的 Value Settings；
- 港组通过调谐物品复制和应用；
- 本地包裹地址沿用 Create 的地址牌或包裹地址交互；
- 运行状态、节点、港组、缓存、流体和错误原因由工程师护目镜显示；
- 远仓监视器负责持续展示 TPS、链路和队列；
- 只有远仓请求器使用仓储界面，因为它需要浏览库存、选择货源网络与接收港组；
- Router 地址、节点身份和密钥属于管理员配置与命令，不进入普通方块界面。

- [x] 保留旧地址路由作为迁移期间的兼容路径；
- [x] 远程订单进入 Create 本地打包流程时，以 `PackagingRequest.orderId` 关联路由；
- [x] 持久保存 Create 订单编号与远仓路由的对应关系，服务器重启后仍可恢复；
- [x] 远仓打包机生成包裹时写入对应 `RemoteRouteData`；
- [x] 原版打包机生成的包裹进入远仓港时，也能按 Create `orderId` 自动补齐路由；

- [ ] 为手动投入的普通 Create 包裹增加港口默认目的港组规则。

完成条件：两位玩家使用相同本地包裹地址下单时，包裹仍能分别前往各自选择的服务器和接收港组。

## 里程碑 1：Transerver 适配层

- [x] 建立唯一的 `TranserverBridge`，DistantStock 只调用 `dev.transerver.api`；
- [x] 在服务器生命周期中安全注册远仓频道；未完成的频道保持 `RETRY`，不会误拒绝持久消息；
- [x] 接入节点 UUID、别名、在线状态和队列统计快照；
- [x] 实现 `network.announce` 的版本化编解码与按变更可靠发布；
- [x] 实现 `stock.query` / `stock.result` 的版本化编解码、目标网络校验与缓存更新；
- [x] 实现有字段与总大小上限的 `order.request` 编解码；目标持久收件箱完成前不启用发送；
- [x] 建立目标服持久订单收件箱；调用 Create 前强制落盘，崩溃后的不确定订单不会自动重复生产；
- [x] 新请求器按 `networkId.nodeId` 直接发送订单；旧请求器保留 HTTP 迁移路径；
- [x] 实现带版本、长度上限和 SHA-256 完整性检查的 `package.dispatch` 编解码；
- [ ] 旧 HTTP 原型进入只读迁移期，随后删除地址、重试与队列重复实现。

完成条件：至少三台节点可以通过同一 Router 发现彼此；修改域名或 Router 地址不会改变已有包裹的目的节点。

## 里程碑 2：包裹托管与兼容检查

- [x] 在来源服建立持久 `EscrowRecord`，保存包裹原始字节、哈希、路线和状态；
- [x] 增加 `PayloadManifest`，只列出本包裹实际引用的物品和数据组件（模组集合由命名空间推导）；
- [x] 目标节点在权威解码前执行注册表兼容性预检；
- [x] 目标服使用自身注册表完成权威解码与包裹语义核对；
- [x] 建立 `parcelId -> APPLIED` 持久账本，重复消息不得重复生成包裹；
- [x] `REJECTED` 从来源托管记录恢复原包裹（来源港已加载且有空间时）；
- [x] 来源港不存在或无法恢复时进入服务器退件箱（`ParcelReturnInbox`，宽限 600 tick 后接管，之后每 100 tick 重试退回原港）；
- [x] 两端均无法解码时进入管理员可见隔离库（`ParcelQuarantine`，保留原始字符串、SHA-256、路线、原因和时间）；
- [x] 迁移为单所有者转换：先持久写入新保管方并落盘，再删除旧托管记录；落盘失败回滚，崩溃窗口由 `reconcile` 收敛到新保管方；
- [ ] 永久拒收的包裹不得被无限重发（当前退回发送缓存后会被再次寄出，需区分永久拒收与可重试拒收）；
- [x] 只有目标主线程实际插入接收港后才返回 `APPLIED`。

完成条件：断线、重启、重复投递、目标缺少模组和目标港满等场景均不复制、不吞物品，并能显示当前保管方。

## 里程碑 3：远仓港完整玩法

- [ ] 六面物品能力统一支持输入与输出，并保持发送缓存和接收缓存分离；
- [ ] Value Settings：发送、接收、双向以及港口优先级；
- [ ] 调谐物品：复制港组、应用港组、清除绑定；
- [ ] 地址牌：设置到达本服后的 Create 包裹地址；
- [ ] 普通包裹使用发送港的可选默认目的港组；
- [ ] 带路由包裹始终优先使用自身目的地；
- [ ] 接收港组在已加载、有空间且可用的港之间轮转；
- [ ] 没有可用港时返回 `RETRY`，不自动改投其他港组；
- [ ] 状态灯接入：青色闪烁表示发送，橙色表示故障；其余颜色保留；
- [ ] 护目镜显示模式、节点、港组、地址、缓存、传输状态和错误原因。

完成条件：玩家只放置远仓港、完成调谐并接入现有物流，即可可靠寄送普通 Create 包裹。

- [ ] 请求器下单时明确选择货源网络、接收港组和到货地址；

- [ ] 更新请求器仓储界面、说明书与思索。

## 里程碑 6：互通塔与资源系统

这一阶段在基础传输可靠后开始：

- 独立远仓港在低负载下可自行工作；
- 普通互通塔集中提供应力、流体、带载、速度和区块加载；
- 世界互通塔提供全世界覆盖与公共吞吐量；
- 传输费用在发送前完成能力检查和资源预留；
- 目标拒收或投递失败时不结算资源；
- 云盘设计为有容量、有归属、可追踪的持久中转仓，不拆解包裹内容。

互通塔结构、流体名称、消耗公式和精确数值继续保留为设计项，暂不写入核心协议。

## 发布前验证

每个里程碑都要保持专用服务器可启动。公开测试前至少完成：

1. 三台 Minecraft 服务器的多向传输；
2. 同地址并发订单与一网多港；
3. Router、来源服和目标服分别断线及重启；
4. 目标服缺少顶层物品、嵌套物品或数据组件；
5. 目标港满、区块卸载和世界卸载；
6. 重复消息、重复回执和乱序回执；
7. 修改节点域名、别名和 Router 地址；
8. Multiverse 世界重命名、卸载与重新加载；
9. 一百次重复提交和故障注入后的物品总量守恒；
10. 目标拒收后进入退件箱，重启后只被退回一次；原港被拆除时仍可用管理员命令恢复。
