# 权限与多人服务器

远仓运行在多人服务器时，最重要的安全边界不是“谁能看到一个按钮”，而是：

> 谁能发现仓库、谁能使用仓库、谁能修改仓库 membership、谁能让远端设备代表自己发订单。

当前版本把这些动作拆成不同权限层，不把“能下单”和“能改网络”混成一件事。

---

## 先看四层身份

```text
玩家
  ↓ 管理 / 使用
远仓网络
  ↓ 包含
Create 仓储网络
  ↓ 绑定
请求台 / 远仓港 / 仪表 / 红石请求器等设备
```

这里最容易误会的一点是：

**远仓网络的成员是 Create 仓储网络，不是玩家。**

玩家拥有管理权、终端上下文和设备操作权，但不会因为自己“加入了远仓网络”就让整个玩家身份变成跨服仓库成员。

---

# Create 权限仍然是本地仓库的第一道门

远仓没有重新发明一套本地仓库 owner 系统。

对于当前服务器上的 Create 网络，它直接调用 Create 自己的：

```text
mayInteract
mayAdministrate
```

两者用途不同。

---

## mayInteract：能不能正常使用

普通使用包括：

- 打开已经绑定的本地请求台；
- 从本地 Create 仓库下单；
- 把远仓设备的来源指向一张自己有权使用的本地仓库。

如果 Create 网络由某个玩家拥有但**没有锁定**，普通非 owner 玩家按 Create 原生规则仍可以获得普通 interaction 权限。

网络锁定后，非 owner 的普通交互会被拒绝。

远仓不会因为设备是“远仓设备”就绕过这层检查。

---

## mayAdministrate：能不能改变结构关系

管理动作包括：

- 第一次把一张本地 Create 仓库加入某张远仓网络；
- 修改本地成员仓库的远仓显示名；
- 修改这张 Create 网络的原生锁定状态；
- 其它明确改变本地 Create / 远仓关系的管理入口。

这意味着：

> “别人允许你从他的仓库下单”

并不自动等于：

> “你可以把他的仓库加入自己新建的远仓网络”。

这是两个权限层。

---

# 为什么不允许客户端浏览全服 Create 网络

旧交互曾经把服务器扫描到的 Create 仓储网络直接作为候选列表显示给玩家。

在单人世界里问题不明显，但在公共服里等于：

- 暴露别人有多少物流网络；
- 暴露网络 UUID / frequency；
- 暴露仓库存在与否；
- 给玩家一个“先看全服仓库，再挑目标”的入口。

当前版本彻底改变了这个模型。

服务器内部仍然可以扫描 Create 网络用于库存与路由工作，但发给客户端的成员目录经过正式远仓网络 scope 过滤。

```text
玩家终端属于 Elysium
→ 只能收到 Elysium 已登记成员仓库
```

一张完全无关的 Create 网络，即使就在同一台服务器，也不会因为“扫描到了”就出现在这个玩家列表里。

---

# Create 仓库怎么加入远仓网络

正常玩家流程要求**物理接触本地仓库**：

1. 远仓港物品先绑定 Create 物流链接；
2. 港放置在该仓库附近；
3. 玩家拿已经加入正式远仓网络的便携终端；
4. 右键这个港；
5. 服务端检查玩家对这张 Create 网络的 `mayAdministrate`；
6. 通过后，才写入正式 membership。

这不是纯 UI 选择，也不是“知道 UUID 就能加”。

它要求玩家实际站在这张本地仓库的设备旁，并通过 Create 管理权限。

---

# 一张 Create 仓库只能属于一张正式远仓网络

服务端 membership 是：

```text
RemoteNetworkId(Create 仓库)
        ↓
Distant Network UUID
```

同一张 Create 网络已经属于正式远仓网络 A 时，不能被另一个终端静默改写成 B。

必须显式离开旧 membership，再加入新的远仓网络。

这条约束是服务端数据层规则，不只是 UI 禁用按钮。

---

# 设备缓存不是权限真相

请求台、终端和其它设备可能保存：

- 上次选中的 Create 仓库；
- 上次看到的远仓 network UUID；
- 接收港组；
- 地址。

这些值可以帮助 UI 恢复状态，但**本地 Create membership 的最终真相在服务器 SavedData**。

因此：

- 两个旧终端即使缓存了不同的远仓 UUID；
- 同一张 Create 仓库也不能因此同时属于两张远仓网络。

服务端会根据当前正式 membership 重新解析。

---

# 为什么远端仓库不检查“当前玩家是不是对面 Create owner”

这点看起来反直觉，但非常重要。

假设：

```text
服务器 A：玩家 Alice 的仓库
服务器 B：玩家 Bob 在下单
```

Bob 不存在于服务器 A 当前玩家对象里，服务器 B 也无法调用：

```text
A.Create.LOGISTICS.mayInteract(..., Bob)
```

如果远仓要求“当前玩家必须是远端 Create owner”，那么跨服协作本身就无法成立。

所以规则分成两段：

### 本地 Create 边界

仓库第一次加入远仓网络时，由**仓库所在服务器**用 Create `mayAdministrate` 做授权。

### 远程使用边界

仓库成为正式远仓成员以后，远程路由按：

- 正式远仓 network membership；
- 设备 / 终端所在 network scope；
- 接收港组权限与存在性；
- 服务端路由验证；

授权跨服使用。

也就是说：

> Create 权限决定“这张仓库能不能被接进远仓系统”；
> 远仓 membership 决定“接进来以后，哪些远仓成员能互相通信”。

---

# Join Code 是加入授权，不是永久密码

Join Code 形式：

```text
AB3D-7K2M
```

它用于让：

- 便携终端；
- 远仓仪表；
- 远仓红石请求器；
- 其它支持该入口的远仓设备；

第一次获得一张正式远仓网络的上下文。

成功以后保存正式 network UUID，不需要每次启动重新输入 Join Code。

---

## 重置 Join Code 会发生什么

创建者重置以后：

- 新设备不能再用旧码加入；
- 新终端不能再用旧码加入；
- 已经加入的终端不会掉线；
- 已经加入的设备不会掉线；
- 已经登记的 Create 仓库 membership 不改变。

因此重置加入码适合处理：

> “旧码已经发给太多人，我不希望继续有人拿它新增设备。”

它不是“立即踢掉所有成员”。

---

# 请求台里的“阻止其他玩家从此处下单”到底锁什么

这个按钮直接对应 Create 原生物流网络的 `locked` 状态。

所以准确语义是：

> 阻止没有 Create interaction 权限的其他玩家通过这张本地 Create 网络下单。

它不是远仓单独维护的一张黑名单。

也不是只锁当前这一台请求台。

如果同一 Create 网络下有多台请求终端，Create 网络锁定状态对它们共享。

---

## 为什么只在固定请求台提供这个按钮

便携终端可能正在查看远端成员仓库。

如果一个便携终端只因为“能看见远端仓库”就可以远程切换对方 Create `locked`，它就会变成跨服管理员工具。

所以当前实现只在固定请求台选中**本地** Create 仓库时暴露这项控制。

并且服务端再次检查 `mayAdministrate`。

---

# 仪表和红石请求器为什么支持 A+B 两种入网方式

## A：Join Code

适合：

- 跨服；
- 没有便携终端在现场；
- 直接给设备配置网络。

## B：便携终端本地右键

适合：

- 同服现场配置；
- 一次连续布置很多设备；
- 不想重复输入 Join Code。

如果终端当时已经选中了成员仓库，B 方式还会把来源仓库一起复制。

如果终端只拥有远仓 network context，则设备只入网，来源仓库以后在 UI 里选。

无论 A 还是 B，最后保存的都是同一个正式远仓 network UUID。

---

# 接收港组也有自己的访问边界

接收港组决定“别人的包裹能不能从我的港出来”。

玩家创建的组可以不是默认公开状态。

因此系统在：

- 玩家把港加入某个接收组；
- 下单选择目的组；
- 服务端解析订单目的地；

都会检查组是否存在、是否属于正确远仓网络，以及当前动作是否允许。

客户端里能看到一个名字，不代表伪造 packet 就可以绕过服务端检查。

---

# 客户端不是权限裁判

远仓所有关键动作都在服务端重新验证。

包括：

- 选择来源成员仓库；
- 本地 Create interaction；
- Create administration；
- 远仓 network scope；
- 接收港组；
- 下单；
- 设备绑定。

所以 UI 过滤是为了减少误操作和信息泄露，但安全不能只依赖“客户端没显示这个按钮”。

即使客户端构造一个正常 UI 不会发送的 packet，服务端仍应拒绝不合法目标。

---

# 多人服务器推荐做法

## 每个组织 / 玩家群体使用独立远仓网络

例如：

```text
Elysium-Industrial
Tomori-Factory
Public-Trade
```

不要因为“都是同服玩家”就把所有仓库全塞进一张大网络。

远仓 network 本身就是隔离边界。

---

## 仓库名用人能看懂的名字

推荐：

```text
中央仓库
机加工车间
原料仓
Parallel 主工厂
```

不推荐长期使用：

```text
9a73f2c1
仓库 1
仓库 2
```

UUID 应该留给系统，不是留给玩家做脑内数据库。

---

## Join Code 不要当公开服务器公告长期挂着

如果某张远仓网络只给固定玩家使用：

- 初次配置时发 Join Code；
- 设备配置结束后可以重置；
- 已有成员不会因此断线。

这样能降低旧截图、聊天记录里的 Join Code 被继续使用的风险。

---

## 需要“公开仓库”时，建专门网络

如果服务器真想做公共交易仓库，建议单独建立：

```text
Public-Trade
```

把愿意共享的 Create 仓库加入这个网络。

不要通过关闭所有权限边界来实现“公共”。

这样私人生产仓库和公共交易仓库仍然有明确 scope。

---

# 当前还没有的权限功能

为了避免 Wiki 把设计稿写成现有能力，下面这些**当前不是正式实现功能**：

- 单独的“允许 / 禁止远程订单”总开关；
- 每个远仓网络的玩家 ACL / 白名单 UI；
- 按玩家记录的远程订单审计面板；
- 终端级别的细粒度只读权限；
- 跨服直接修改对方 Create owner / locked。

当前真正存在的安全边界是：

```text
Create 本地 owner / lock
+ Create mayInteract / mayAdministrate
+ 正式远仓 network membership
+ 服务端 scope 校验
+ 接收港组校验
+ live receiver probe
```

如果后续增加更细粒度 ACL，应在这一层之上继续加，而不是替换这些基础边界。

---

# 一个简单的安全判断

如果你不知道某个动作应该用哪层权限，问：

> 这个动作是在“使用已经授权的仓库”，还是在“改变谁拥有/共享这张仓库”？

如果只是使用：

```text
mayInteract
```

如果会改变 membership、锁或本地网络管理关系：

```text
mayAdministrate
```

如果目标是远端仓库：

```text
正式远仓 network membership + 服务端路由规则
```

这就是当前权限模型的核心。
