# 路由与包裹

远仓不是“把物品从 A 瞬移到 B”。

一笔完整运输会经过几层不同的身份与目的地：

```text
远仓网络
  ↓
来源成员仓库
  ↓
目标节点
  ↓
接收港组
  ↓
跨服包裹
  ↓
目标服务器本地 Create 包裹地址
```

把这些层分开以后，很多“为什么它没从这个港出来”“为什么包裹落地后去了另一条线”的问题就很好解释了。

---

## 一条远仓路线真正保存什么

远仓包裹的跨服路线 `RemoteRoute` 当前保存：

- schema version；
- 目标 Transerver 节点 UUID；
- 接收港组 UUID；
- correlation UUID；
- child order UUID。

它**不保存 IP、域名或 Router URL**。

物理网络连接属于 Transerver；游戏里的路线只保存稳定逻辑身份。

---

## 远仓网络是最外层命名空间

目标接收港组不是全服全局名字。

它首先属于一张正式远仓网络：

```text
Elysium
└─ Main

Other-Network
└─ Main
```

两个 `Main` 可以同时存在，因为它们位于不同远仓网络 scope。

发货前系统会确认：

- 路线携带的是正式远仓网络；
- 目标接收港组也属于同一张远仓网络；
- 远端确实还有符合这两个条件的可用接收端。

因此“名字一样”不会让两个不同远仓网络串包。

---

## 接收港组决定跨服落点

接收港组回答的是：

> 这个包裹到目标服务器后，从哪一组远仓港出来？

例如：

```text
接收港组：Factory-A
├─ 港 1 · 优先级 5
├─ 港 2 · 优先级 5
└─ 港 3 · 优先级 2
```

系统先选择**最高优先级里仍有空间**的候选。

相同优先级的可用港会按稳定顺序轮换，避免所有流量永远砸在第一台港上。

如果高优先级港满了，仍可选择下一档有空间的港。

---

## Create 包裹地址决定落地后的本地路线

接收港组和 Create 包裹地址不是一回事。

例如：

```text
跨服落点：Factory-A
本地地址：Gear-Line
```

运输过程：

```text
远端服务器
  ↓
接收港组 Factory-A
  ↓
某一台可用远仓港
  ↓
包裹离开远仓港
  ↓
本地 Create 物流按 Gear-Line 继续分拣
```

所以一个接收港组完全可以承接很多不同 Create 包裹地址。

港组负责“从哪里登陆”，Create 地址负责“登陆以后去哪”。

---

## 为什么跨服包裹需要两套地址

跨服前后两台服务器各有自己的本地 Create 地址空间。

一件包裹在来源服务器上可能需要先经过一个来源侧地址，而到了目标服务器以后，又应该换成目标侧 `homeAddress`。

远仓因此会把目标侧地址作为额外路由数据随包裹携带。

跨服落地时：

1. 远仓读取目标侧 `homeAddress`；
2. 把 Create 包裹本身的地址切换为这个目标地址；
3. 清掉已经用完的 `homeAddress` 临时字段；
4. 后续完全交回本地 Create 包裹物流。

如果没有设置目标侧地址，远仓不会凭空猜一个。

---

## 包裹 Tooltip 为什么能显示人类可读目的地

真正的路线内部是 UUID：

```text
目标 Node UUID
接收港组 UUID
```

这对玩家没什么可读性。

因此写入路线时，远仓还会把当时的人类可读标签一起写进包裹数据，例如：

```text
Parallel · 主工厂接收口
```

客户端看 Tooltip 时不需要自己再访问服务器目录才能知道目的地。

如果一件旧包裹没有这个标签，才会退回到较短的 ID 显示。

---

## “跨服”状态不是永久贴纸

旧实现曾经给包裹写一个类似“CrossServer”的永久标志，问题是包裹已经到达以后这个标志仍然留着。

当前实现不再这样做。

系统会根据路线目标节点是不是**当前节点**动态判断这件包裹是否仍处在跨服旅途中。

所以一件已经落地的包裹不会永远显示“还在跨服”。

---

# 发货前：先确认真的有人能收

## 网络公告不是发货许可证

其它节点定期公布仓库和接收端状态，但公告可能已经有几秒延迟。

远仓不会因为“上一次公告说有接收港”就立刻把真实物品交出去。

真正发货前会做一次 **Receiver Probe**。

---

## Receiver Probe 检查什么

发送端询问目标节点：

```text
目标远仓网络 UUID
+ 目标接收港组 UUID
```

目标端只有在以下条件成立时才回答 available：

- 远仓网络仍然有效；
- 接收港组仍存在；
- 该组仍属于同一张远仓网络；
- 当前至少有一台真正可收件的远仓港。

“真正可收件”意味着：

- 不是纯 SEND 模式；
- 港没有满；
- 方块实体确实加载在服务端；
- 港处于运行中的互通塔带载状态。

---

## Probe 的确认非常短

远程 positive answer 只有很短的有效期，并且：

> **一个成功回答只授权一个包裹。**

第一个包裹真正离开以后，这个 positive answer 会被消费掉。

下一件包裹需要重新确认。

这样不会出现“一次探测说能收，随后 20 个包裹一起冲过去”的情况。

---

## PENDING / UNAVAILABLE

第一次发出 probe 后，状态可能短暂为 `PENDING`。

如果目标及时回答，就转为：

- `AVAILABLE`；或
- `UNAVAILABLE`。

如果一个完整等待窗口过去都没有有效答复，发送端不会永远静默等待，而会把目标视为当前不可用，同时后台继续重试。

---

## 没有可用 receiver 时不会发生什么

目标端不可用时，包裹：

- **不会离开发送港**；
- **不会进入 Parcel Escrow**；
- **不会为这次失败扣以太**；
- **不会因为旧公告而强行交给 Transerver**。

同时：

- 港显示明确的“无可用接收端”原因；
- 日志系统记录 `DOCK_NO_RECEIVER` WARN；
- 不再额外叠一条泛化的“outbound stuck”告警制造重复噪声。

恢复接收端以后，原包裹继续尝试发送。

---

# Parcel Escrow：谁现在拥有这件物品

跨服务器运输最危险的问题不是“消息发没发出去”，而是：

> 这件真实物品现在究竟归谁保管？

远仓用 `ParcelEscrow` 解决这个问题。

---

## HELD

包裹准备跨服时，来源服务器先把它编码并写入持久 escrow 记录。

这表示：

> 来源服务器仍然对这件包裹负责。

Escrow 会记录：

- parcel UUID；
- 完整编码后的包裹；
- 地址；
- 目标节点；
- 接收港组；
- 来源维度和方块位置；
- 创建时间；
- 当前状态；
- 对应 transport message UUID。

---

## SUBMITTED

Transerver 已经接收本次发送以后，escrow 进入 submitted 状态。

这仍然不等于“物品已经安全落地”。

真正的完成条件是目标端明确返回成功结果。

---

## APPLIED 才算真正交接完成

目标端成功验证并接收包裹以后，才返回 `APPLIED`。

来源端收到确认后，才可以把对应 escrow 记录删除。

这就是远仓避免复制 / 吞包的核心原则：

```text
消息提交成功
≠
物品交付成功
```

---

## REJECTED

如果目标明确拒绝包裹，来源端会保留拒绝状态与原因，而不是当作成功完成。

后续恢复逻辑可以据此：

- 返回原港；
- 进入服务器退件箱；
- 做兼容性处理；
- 或进入隔离流程。

---

# Mod 不一致与 Payload Manifest

跨服包裹可能包含目标服务器根本不存在的：

- 物品 ID；
- 数据组件类型。

因此目标端在真正解码前可以先检查 payload manifest。

这比“直接反序列化，炸了再说”更安全。

当目标服务器缺少必要注册项时，系统不会假装包裹已经正常落地。

管理员应优先检查两端 Mod 版本一致性，并通过隔离 / 导出工具确认数据，而不是强行丢弃。

---

# 回退、退件箱和隔离库

它们是三个不同层级。

## 港底面回退

这是最靠近机器的一层。

能在本地恢复的 stranded 包裹、无法继续发送的普通内容，会优先从远仓港底面回退出口交回自动化。

适合接：

- 箱子；
- 保险库；
- 溜槽；
- 报警检测。

---

## 服务器退件箱

如果已经无法可靠回到原远仓港，包裹会进入服务器侧持久退件记录。

管理员可以：

```text
/distantstock returns list
/distantstock returns restore <id>
/distantstock returns give <id>
/distantstock returns export <id>
```

它仍然被当成“需要恢复的真实物品”。

---

## 隔离库

如果问题已经不是普通路由失败，而是：

- 编码 / 解码不兼容；
- 注册项缺失；
- 数据不能安全应用；

内容会进入隔离库。

```text
/distantstock quarantine list
/distantstock quarantine give <id>
/distantstock quarantine export <id>
/distantstock quarantine discard <id>
```

`discard` 是明确删除，不是普通“清警告”操作。

---

# 一笔包裹的完整生命周期

正常跨服时：

```text
订单建立远程路线
  ↓
来源 Create 仓库真实打包
  ↓
包裹携带 RemoteRoute
  ↓
进入发送端远仓港
  ↓
Receiver Probe
  ↓
AVAILABLE
  ↓
结算塔运输条件 / 以太
  ↓
写入 Parcel Escrow
  ↓
提交 Transerver
  ↓
目标服务器验证远仓网络和接收港组
  ↓
选择可用接收港
  ↓
应用目标侧 homeAddress
  ↓
交给目标本地 Create 物流
  ↓
返回 APPLIED
  ↓
来源端删除 escrow
```

这条链里，任何一步失败都应该留下“谁还拥有真实物品”的答案。

这比“尽量把包裹送到”更重要。

---

# 多港系统怎么选

同一接收港组中：

1. 先看谁真正可接收；
2. 再看优先级；
3. 只在最高可用优先级层里选择；
4. 同优先级按稳定轮换分流。

所以可以设计：

```text
主收货港 A · priority 5
主收货港 B · priority 5
备用港 C   · priority 2
```

A / B 正常时分担流量；两者都不可用时 C 才接管。

---

# 排查路由问题时记住一句话

不要只问：

> “目标服务器在线吗？”

应该依次问：

```text
远仓网络对吗？
↓
目标节点对吗？
↓
接收港组对吗？
↓
现在真的有可用 receiver 吗？
↓
包裹是否仍在源港 / escrow / 目标港？
↓
落地后的 Create 地址对吗？
```

只要这六个问题能回答，跨服包裹基本就不再玄学。

# 本地锁链诊断、Ping 与缓存接管

这一层只处理**当前服务器上的 Create Chain Conveyor 包裹网络**，和前面的跨服 Receiver Probe 不是同一套机制。

## 无路由包裹

如果一个普通包裹在当前锁链路由表里找不到任何匹配地址：

```text
有诊断蛙港
→ 路由到诊断蛙港
→ 进入 18 格异常包隔离库存
→ CHAIN_NO_ROUTE

没有诊断蛙港
→ 保持 Create 原行为
→ 包裹继续在锁链上游荡
```

正常能到达目的 Frogport 的包裹不会被诊断蛙港抢走。

## Ping 包

诊断蛙港会依次检查链路中的接收地址，并生成系统 Ping 包。

Ping 仍然是真正的 Create PackageItem，因此会沿 Chain Conveyor 正常移动、被目标 Frogport 正常接收，玩家也能把它从锁链上取下来。

玩家取走 Ping 时，本轮该地址检测记为 **SKIPPED**，既不判故障，也不判恢复。

这只 Ping 随后会被标记为失效；再放回锁链时只会返回原诊断蛙港被回收，不能用一只迟到的 Ping 误判“已经恢复”。

## 动态超时

Ping 不使用固定全服秒数。

远仓读取 Create `ChainConveyorBlockEntity.ConnectionStats.chainLength()`，沿实际连接图计算目标的物理链长，并结合当前链轮转速估算到达时间。

因此：

- 近距离、高速链路的等待时间更短；
- 远距离、低速链路会获得更长 deadline；
- 计算结果带安全余量，并限制在 5–120 秒之间。

Create 路由表里的 `distance` 只是经过 Chain Conveyor 节点的跳数，不直接当作物理距离。

## 堵塞后的地址接管

某个业务地址 Ping 超时以后，该锁链网络中的同地址正常 Frogport 会被临时换成各自唯一的恢复地址，缓存蛙港同时接管原业务地址。

```text
业务地址：批量洗涤接收

正常状态：
  Frogport A → 批量洗涤接收
  Frogport B → 批量洗涤接收

故障状态：
  Frogport A → 私有恢复地址 A
  Frogport B → 私有恢复地址 B
  缓存 Frogport → 批量洗涤接收
```

这样普通货流进入缓存，恢复 Ping 仍然能准确命中原来的每一台 Frogport。

所有被冻结 Frogport 都收到一次按时 Ping 后才解除接管。

## 区块卸载和服务器重启

目标区块未加载时不会被视为“已经恢复”。恢复检测会暂停，等目标重新加载以后继续。

缓存蛙港的 54 格库存和重发设置保存到方块实体 NBT；如果服务器硬崩导致运行时 fault 状态丢失，重启后缓存蛙港会自动放弃孤立的业务地址接管，但保留已经缓存的包裹，再按设定速度回放。

持久 EventRegistry 中已经没有 live fault 对应的旧 `CHAIN_PING_TIMEOUT` / `CHAIN_CACHE_FULL` 会自动转成历史记录，避免重启后出现幽灵报警。
