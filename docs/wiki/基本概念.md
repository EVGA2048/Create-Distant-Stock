# 基本概念

远仓最重要的不是机器数量，而是把“Create 仓库”“远仓网络”“设备上下文”和“包裹目的地”分清楚。

---

## Create 仓储网络

这是 Create 自己的物流网络，也是远仓读取库存和提交订单的基本单位。

一张 Create 仓储网络仍然有自己独立的：

- 库存；
- 仓储链接；
- 打包设备；
- 本地地址；
- Create 物流网络 UUID。

远仓不会替代 Create 的权限模型。本地网络是否允许普通玩家交互、是否被锁定、谁能管理，仍由 Create 自己决定。

远仓使用两种 Create 权限：

- **普通交互权限**：使用已经绑定好的本地请求设备、从本地仓库下单、把设备指向可访问的本地仓库；
- **管理权限**：第一次把本地 Create 仓库加入某张远仓网络、修改仓库名称、切换 Create 原生锁定状态等管理动作。

---

## 远仓网络

远仓网络是跨服路由的正式命名空间。

它回答：

> 哪几张 Create 仓库属于同一套远仓系统？

例如：

```text
远仓网络「Elysium」
├─ ES2 · 中央仓库
└─ Parallel · 主工厂
```

**真正的成员是 Create 仓储网络。**

一个玩家可以创建和管理多张远仓网络，但一张 Create 仓储网络同一时间只能属于一张正式远仓网络。

### 终端可以先入网，仓库以后再加

便携式远仓终端本身可以先创建或加入一张远仓网络，而暂时不选择任何 Create 仓库。

随后拿这个终端去右键一台已经绑定本地 Create 网络的远仓港，才会把港背后的整张 Create 仓库正式加入远仓网络。

这两个动作是故意拆开的：

```text
终端加入 Elysium
        ≠
Create 仓库加入 Elysium
```

### 设备加入远仓网络不等于仓库 membership

远仓仪表和远仓红石请求器可以通过：

- 8 位加入码；
- 已加入远仓网络的便携终端本地右键配对；

获得一个远仓网络上下文。

然后设备才能从**该远仓网络的成员仓库**中选择来源仓库。

这不会让设备自己变成“仓库成员”，也不会改变任何 Create 网络的 membership。

---

## 仓库成员名称

Create 的网络 UUID 不适合玩家辨认。

一张本地 Create 仓库第一次通过远仓港加入远仓网络时，系统会给它分配一个默认名称，例如：

```text
Frank 的仓库
Frank 的仓库 2
```

有管理权限的玩家可以在远仓网络页面修改本地成员仓库名称。

这个名称只属于远仓的 member metadata，不会修改 Create 自己的网络身份。

---

## 为什么看不到全服所有 Create 网络

服务器内部的 `StockScanner` 可以扫描本服 Create 网络，但这些扫描结果不会原样发给普通客户端。

客户端仓库列表的规则是：

```text
终端没有正式远仓网络
→ 0 个可见成员仓库

终端属于 Elysium
→ 只发送 distantNetworkId == Elysium 的成员仓库
```

远仓仪表和远仓红石请求器的来源仓库列表也使用同样的 scope 过滤。

因此公共服玩家不会因为打开一个请求界面，就获得全服所有玩家 Create 网络的目录。

## 加入码与正式 UUID

加入码是给人输入的授权凭证：

```text
AB3D-7K2M
```

格式实际为 8 个字符，界面自动按 `4-4` 显示。输入时大小写不敏感，连字符可以省略。

远仓网络内部仍有真正的 UUID，但正常玩家不需要手抄它。

加入码重置后：

- 已经加入的终端不掉线；
- 已经登记的仓库 membership 不改变；
- 已经配置好的设备不改变；
- 旧加入码不能再用于新的加入。

---

## 本地仓库与远端仓库

“本地/远端”相对于当前服务器而言。

- **本地仓库**：Create 网络真实存在于当前服务器；
- **远端仓库**：其它 Transerver 节点在同一远仓网络中公布出来的成员仓库。

本地仓库可额外执行需要 Create 权限的动作，例如入网、改名、锁定。

远端仓库只作为远程货源与状态视图，不允许当前玩家跨服修改对方 Create 本地权限。

---

## 请求设备的绑定顺序

现在推荐把绑定理解成两层：

```text
第一层：这台设备属于哪张远仓网络？
第二层：在这张远仓网络里，它当前选择哪座成员仓库？
```

例如远仓仪表：

```text
加入 Elysium
   ↓
来源列表只出现 Elysium 成员
   ↓
选择 Parallel 主工厂
   ↓
设置物品与目标库存
```

这和过去“先浏览所有 Create 网络再选一个”的模型不同。

## 接收港地址

接收港地址是一组负责接收远仓包裹的港。

```text
接收港地址「Factory-A」
├─ 港 1
├─ 港 2
└─ 港 3
```

包裹只需要知道目标接收港组，不需要知道具体方块坐标。

同名地址可以存在于不同远仓网络中，互不冲突。

---

## 包裹地址

Create 包裹地址负责落地后的本地分拣。

```text
接收港地址 = Factory-A
Create 包裹地址 = Gear-Line
```

远仓先决定包裹在哪组港落地，本地 Create 物流再继续按包裹地址处理。

---

## 互通塔与 Transerver

二者解决不同问题：

- **互通塔**：游戏内设备是否有工作范围、设备容量、区块加载与以太成本；
- **Transerver**：服务器节点之间的消息与包裹传输。

一个设备可能 Transerver 通信正常，但因为不在运行中的互通塔覆盖内而不能工作。

---

## 节点身份与 transport 状态

Transerver 的稳定 NodeIdentity 和 transport 是否在线是两件事。

本机即使暂时关闭跨服 transport，也仍然有稳定节点 UUID，可用于保存本地远仓身份和单机/同服正式远仓网络。

只有真正需要跨节点发送消息时，才要求 Transerver transport 在线。

---

## 包裹不是一次性消息

远仓对包裹做持久化交接，而不是“HTTP 成功就算物品到了”。

因此：

- 重复收到同一包裹不会复制物品；
- 目标港暂时不能接收时会保留并重试；
- 发货前会确认目标远仓网络和接收港组仍然存在；
- 无法安全恢复的内容进入退件或隔离流程，而不是直接删除。

更完整的交接、Receiver Probe、Escrow 与退件流程见：[路由与包裹](路由与包裹.md)。
